- **Description**: The FHIR specification states that an FMM level allows implementers to judge how advanced, “and therefore stable,” an artifact is and that higher maturity levels impose greater controls on breaking changes. The criteria do not provide a consistent basis for either conclusion.

FMM combines multiple independent dimensions—including build quality, interoperability testing, ballot experience, publication history, production adoption, geographic adoption, and change governance—into a single ordinal value. It does not distinguish the stability of a published version from compatibility with future versions, and its R6 definition of a breaking change is based on resource-instance conformance even though changes to API and behavioral requirements can break conformant applications without invalidating existing resource instances.

Furthermore, after reviewing the "source-of-truth" FMM on the Confluence page

https://confluence.hl7.org/spaces/FHIR/pages/35718679/FHIR+Maturity+Model

vs. the definition published across 3 versions of the base specification. (Why is this 2024 source-of-truth document not in the latest FHIR build version?)

The source-of-truth FMM definition describes maturity in terms of the level and types of review an artifact has received. Its levels combine heterogeneous evidence including build QA, work group readiness, interoperability testing, ballot review, scope review, publication history, production adoption, and change governance. Some criteria have alternative means of satisfaction, and any criterion may be waived with FMG approval.

Consequently, an FMM level does not uniquely communicate either the evidence supporting the level or the stability characteristics an implementer is told to infer from it. In particular:

The model does not distinguish maturity from stability or define an empirical relationship between them.
FMM4 may be reached based on sufficient stability and/or widespread use, so advancement can occur without an explicit determination that the artifact is sufficiently stable.
“Tested across scope” can represent implementation testing, expert review, or mapping to an implemented standard, which provide materially different evidence of implementation maturity.
Any criterion may be waived, but the FMM number does not identify waived criteria or expose the evidence supporting the assigned level.
The model does not distinguish stability of a particular published version from compatibility of implementations across subsequent versions.
The R6 breaking-change definition is expressed in terms of previously conformant resource instances, while important implementation-guide changes—such as search requirements, CapabilityStatement requirements, and other API or behavioral requirements—can affect application compatibility without making existing resource instances non-conformant.

For a widely deployed implementation guides these limitations make a single FMM value insufficient to support the implementer-facing stability inference made by the FHIR specification.

US Core provides a concrete example. Beginning with STU 9, US Core replaced the generic FHIR Maturity Model criteria with US Core-specific maturity levels that account for production adoption, regulatory and certification experience, artifact type, and forward-compatibility commitments.

FHIR should either narrow the claims made for FMM or revise the model so that its displayed maturity levels have defined, evidence-based, and consistent semantics for the stability characteristics implementers are told to infer from them.
