- **Description**: Projects are starting to use Communication as equivalent to MessageHeader - which is a problem. We need to clarify the scope of Communication and MessageHeader so that everyone knows when each should be used.

As examples: Da Vinci PDex is using CommunicationRequest to ask for documentation to be shared and then Communication to document that the information was shared (and doing the sharing as part of that). I think this is ok because it's happening at the provider level (providers asking for the data, providers prepping and providing the data.)

Da Vinci Alerts, on the other hand, is using Communication within a Bundle to essentially do the equivalent of v2 ADT messages sending notifications that patient has been admitted, patient has been discharged, lab result has been received, prescription has been cancelled, etc. That seems to be stepping squarely into the space expected to be covered by messaging.

However, there is no guidance in MessageHeader, Communication or messaging section that explains what the boundaries are. We desparately need to provide such language - and get consensus on what the boundaries should be.

### 4. Michelle Miller - 2019-09-17

+ Patient Care WGM Tues Q3 (Sept 17, 2019) discussion +

Messaging is a framework that allows communicating a bunch of resources at once when query is not supported or has limitations (e.g. need to send all data that user might need at once), and event-driven or async responses (days or weeks later) - may not know the final endpoint.

Communication is independent of paradigm (e.g. REST vs messaging). Expose in clinical record that certain data has been communicated. Can identify the specific data or describe the data in coded terms (e.g. smoking cessassion). Because Communication can convey specific payload, it can also be used for transport in addition to record. For example, existing implementations of Communication/CommunicationRequest used for secure email over FHIR. Using Communication as a means for transport is useful, but no specific boundaries exist yet.

However, Communication boundaries currently say "This resource is a record of a communication that has occurred. It does not represent the actual flow of communication."

Can Communication be used for "what" the communication is?

It doesn't matter how the communication occurred (SMS, email, phone, FHIR, v2, CCDA etc), this is the record of the communication.

CommunicationRequest represents the authorization or the order for communication to occur.

The trigger to act upon the authorization (e.g. all lab results sent to Dr Smith) will cause a specific transfer to occur (via FHIR or otherwise). Communication would represent that it was done as part of the CommunicationRequest authorization.

During care planning, recommendation to do a referral, then there can be a ServiceRequest with intent = proposal. Reviewed http://build.fhir.org/workflow-communications.html#12.9.2.2. Task is how you can ask for fulfillment. Multiple scenarios of who owns the Task. The other system can subscribe or pull the task. Or, the task could be maintained on multiple systems (more complex).

When asking for stuff to be done, *Request is needed, which defines in detail what needs to happen (e.g. patient doesn't need Rx for OTC, but use MedicationRequest to describe instructions even though there isn't an order. Or, can create a Task, alone, without an order/request). Task is optional whether it's needed to initiate action.

If there is *only one recipient *(single system) and *don't need a response or status *(assume it will happen or someone will call - no electronic monitoring), then it's ok to send CommunicationRequest (without Task and without any Communication) and get the DiagnosticReport (for example) back. Just defining what to share, what Endpoint is more complex than Task can handle. On the response side, the traditional interpretation of Communication: CommunicationRequest > post to target system or task or operation > data flows via V2 or FHIR or whatever > Communication instance describes what happened, when it happened.

DaVinci's use case doesn't want multiple interactions. The sharing of the data + the record of the sharing are different events. Communication wasn't intended as transport mechanism (but discussing today whether it can be). Still use one transmission - authorization + record, but heavier than like. The lighter weight proposal was to put Bundle being communicated inside Communication.

An order for blood. Task is about request for action. Observation can be used for patient's acuity at a point in time. We don't have resources to support getting more people/staff on the floor. Could be a Task (need someone on ward 3 to do X during time period Y).

Communication is being done all the time (passing around results, orders) - don't need CommunicationRequest for that stuff. Use Communication resource when the action isn't administering blood, transferring a patient – when the action is disclosing information to someone (smoking cessassion) - it's about the information. For example, I want to share the lab results with another provideer. It isn't about authorizing the lab result to begin with.

Boundary clarification needed between:* CommunicationRequest vs Task* Communication vs MessageHeader

No choice, but to include in payload what was communication – when the thing that was communicated doesn't have outside existence. Record may contain the content (since that content doesn't live elsewhere)

1) Data that was conveyed does exist outside – is it still reasonable to package as the content?2) Send a bundle as a transaction that says here is what was communicated and will convey as other resources what was communicated as a package vs separate stuff

Some regulatory requirements don't support pull – must push data. EHR must push data to them. They can't query EHR.

Possible outcome: Communication is always the record, and never the transport (secure email).

Messaging has more capabilities.

Julia would like to align resources with intuitive meaning.

Next steps: Lloyd will draft and socialize use cases, when Communication has to be used, when Communication contains content, when Communication is used as delivery mechanism. This will certainly include DaVinci use cases.

After it's been socialized, then we will schedule a Patient Care FHIR conference call.
