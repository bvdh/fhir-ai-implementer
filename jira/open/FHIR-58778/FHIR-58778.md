- **Description**: `TestScript.setup.action.operation.type` identifies the FHIR interaction or operation to perform. For most interaction types, this also determines the HTTP method. `operation.method` can override that method regardless of the other operation details.

This provides two ways to determine a fundamental part of the operation and allows combinations whose intended behavior is unclear. For example, a test script can combine a `read` operation type with the `post` method.

The specification states that the primary purpose of `method` is to support invoking a FHIR search using HTTP POST. It also mentions negative testing, but does not define which combinations are valid or how engines should interpret contradictory combinations.

A leaner and less ambiguous TestScript structure would have one authoritative way to identify the operation, with targeted representations for genuine variations.

Could `operation.method` be deprecated in favor of `operation.type`? One possible solution for the search use case would be to add explicit operation types such as `search-get` and `search-post`.

Alternatively, if `method` is retained specifically to distinguish GET and POST searches, could the ValueSet bound to this element be restricted to `get` and `post`, and could its use be limited to search operations?

If broader HTTP method overrides remain necessary for negative testing, could `method` instead be defined as a specifically scoped exception, with its allowed use and interaction with `operation.type` clearly defined?
