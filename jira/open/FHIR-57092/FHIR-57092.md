Add an additional bullet to 10.1.5.7 Refining the interpretation of an Observation using additional codes or Observations (#refine), with text as follows:

Understanding the semantics of the Observation may involve combining the semantics of Observation.code with the semantics of other elements such as Observation.bodyStructure, .interpretationContext, and .method. Observation.code may also contain codes that incorporate some or all of those other semantics. Observation.code may thus contain multiple codes which are not semantically identical to each other, but when combined with the rest of the Observation resource are semantically consistent with each other. Implementation Guides may constrain such usages, perhaps to facilitate efficient query strategies or coding consistency.

A reference also needs to be added to the terminology documentation: https://build.fhir.org/terminologies.html#4.1
- **Change Category**: Clarification
- **Request in-person**: KevinO'Donnell
- **Description**: The example/guidance in https://build.fhir.org/observation.html#refine shows multiple codes with semantics that overlap but are not the same.

The description of .coding describes multiple codings as meeting the requirement "Allows for alternative encodings within a code system, and translations to other code systems." But elsewhere the text does note that "When multiple codes are present, the intersection of their meanings SHALL NOT be empty" and allows for codes to have different "granularity".

If this is OK, IDR would like to consider using this for fully pre-coordinated codes to supplement the post-coordinated codes.

The Observation.code comments start to explain how to understand the full semantics of the Observation and the meaning of multiple codes. It might help to add text along the lines "Observation.code may contain post-coordinated codes that are intended to be understood combined with other Observation element semantics like the .bodyStructure and/or the .interpretationContext. It may also contain post-coordinated codes that duplicate those other semantics into Observation.code. Or it may contain both, perhaps to facilitate various efficient query strategies. Such usages may be constrained in Implementation Guides."
