- **Description**: TestScript.*.action.assert.contentType compares an expected media type with the Content-Type header of a request or response.

The same expectation can be represented using the generic header assertion:

"direction": "response",
"headerField": "Content-Type",
"operator": "equals",
"value": "application/fhir+json"

The R5 comments already direct authors to headerField when more control over the value is required. The current Testing IG changes the terminology binding of contentType to Supplemented Mime Types, but retains both assertion mechanisms.

This leaves two representations for the same header expectation. It also makes contentType the less flexible representation, because headerField and value can express the complete header value, including parameters when these are relevant to the test.

A leaner TestScript specification should use the generic header mechanism as the authoritative representation, unless contentType has distinct comparison semantics. Such semantics—for example normalization of media types or treatment of parameters—are not currently defined.

Could TestScript.*.action.assert.contentType be deprecated in favor of headerField, operator and value? If contentType is retained, could the specification define which behavior cannot be represented by a generic Content-Type header assertion?
