- **Description**: Since the changes to ConceptMap ins R5, concept maps can say very explicitly that there's no map for a concept. But the $translate operation can't say this - it can fail to mention a map, but it can't report that a concept map us explicitly stated that there is no map for a concept in a ConceptMap

We should define match.noMap 0..0 boolean for this purpose - to explicitly say that the originMap(s) says: there is no map for this concept

## Comments

### 1. Michael Lawley - 2026-10-04

+1. Note cardinality should be 0..1, not 0..0.

The tx-ecosystem tests already assume this part (translate-4, 1.9.6), so it would help to pin down the surrounding semantics at the same time:

result: the result definition currently only excludes not-related-to. It should also say that a match with noMap = true is not a translation, i.e. result can only be true if at least one match has a concept with a relationship other than not-related-to. (The ecosystem IG currently disagrees with itself here: the translate-4 fixture and 1.9.6 history say result = false, while requirements.md says true.)
Co-occurring parts: when noMap = true, concept and relationship SHALL NOT be present.
Other parts: translate-4 also expects sourceComment (from group.element.comment) and sourceConcept, neither of which is defined in the current OperationDefinition. Either add them here or in a companion ticket.
R4: noMap should be reported the same way when the R4 map uses a codeless target with equivalence = unmatched.
unmapped: worth restating that a noMap element suppresses group.unmapped for that code, so no fallback match is produced alongside the noMap match.
