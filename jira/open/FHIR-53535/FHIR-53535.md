### 4. John Moehrke - 2026-06-08

Do not tie this ticket to policyBasis improvements. This ticket has nothing to do with policyBasis. That said, having multiple policyBasis will bring up the question of how to combine those multiples. By forcing ONE, this combining problem becomes the responsibility of that ONE policyBasis.

### 5. John Moehrke - 2026-05-26

This ticket is different than you are thinking about. One can always use the .policyBasis.reference to point at a computable form of the backing policy.

This ticket is about when there is a desire to put the patient specific terms (aka .provisions) into a Permission resource. This was allowed in past FHIR core ballots, but was removed when Permission was moved out to an incubator IG. At that time we had to remove the element and invariant. This ticket restores the functionality using an extension defined in the Permission incubator IG (following the advice from FHIR-I and product director). So in this case there should not be both Permissions specific to this patient, and .provisions specific to this patient.

### 6. Mohammad Jafari - 2026-05-26

Can we model this as a Permission resource referenced in `policyBasis.reference`? I also don't think we should disallow using provisions in that case because it is conceivable a broad policy is referenced there and provisions will further refine it by articulating exceptions.

I recognize this still leaves us with the issue of how to model if we want to model those further refinements also as a Permission resource in which case we need an additional element.
