- **Description**: The Descriptions still says: "Identifier by which this case can be referenced."

That definition was adequate for 0..1, but now that multiple identifiers are explicitly allowed, it would be useful to explain why a regulatory case may have multiple identifiers, for example identifiers assigned by different regulators, systems, procedure stages, or jurisdictions.

Without guidance, implementers may not know whether multiple identifiers represent aliases for one case or separate regulatory procedures.

Suggested change:

Update the definition/comments to explain the intended use of multiple case identifiers.

Suggested wording:

"Business identifiers by which this regulatory case can be referenced, including identifiers assigned by different regulatory authorities or systems."

## Comments

### 1. Rik Smithies - 2026-09-23

I sympathise but I think the use of multiple identifiers is too general to be described. Multiple identifiers on the resource all apply to the resource. How exactly they apply is up to implementers, and the standard cannot say much about it.

It is FHIR standard pattern to allow multiple identifiers, because it is common in general for the same concept to be given multiple identifiers, possibly by different entities. How or why or what they signify is hard to predict (but all are perfectly legal).

Implementers can use the normal parts of the identifier data type (system, assigner, type) to detail what these identifiers are, or can detail this in implementation guidance. This is just standard FHIR however, not specific to this resource.

I don't know what else we can say that would help. There is no hidden meaning here that we can document.
