When sorting on search parameters of date type, if the source data is not a single instance (e.g. a Period) the sort behavior is server-defined. to
When sorting on search parameters that contain ranges of values (e.g. a date period, range of numeric values, etc.) the sort behavior is server-defined with respect to selecting a value. If more prescribed search behavior is needed, custom search parameters that assert specific behavior can be defined (e.g., a parameter targeting the Period.end)). While most reference implementations search by the lower bound of the period/range, it is recommended to use the lowest/earliest value an element touches when sorting in ascending order and the highest/latest value an element touches when sorting in descending order.

### 4. Bas van den Heuvel - 2024-09-11

ginocanessa, some further thoughts on this topic.

Any date/datetime value is a representation of a period. A value of 2010-08 indicates a period between 2010-08-01T00:00:00 and 2010-08-01-31T23:59:59. A similar approach could also be taken for day, hour, minute and second.

Although the specification indicates an exception for sorting on periods (is server defined), such exception would also apply to sorting DataTime instances where some include seconds and others do not.

Search is normative so I do not think we should introduce mandatory guidance. We could consider adding the following algorithm as a suggestion:

when sorting in ascending order, the start of the period should be used.
when sorting in descending order, the end.

This will place the instance always as the first entry in its virtual period.
