- **Description**: The Operation Execution section in testing.html states:

Operations that are expected to result in an error or exception shall immediately be followed by one or more "assertion" operations (that test for those error conditions), otherwise the test fails. This allows for "negative" testing (for example, the test script may perform operations that should return a 4XX or 5XX HTTP response code).

This appears to imply that determining whether an operation passes or fails is deferred until the first assertion following the operation has been evaluated, and that the operation result depends on the result of that assertion.

However, the operation itself was executed and produced a response that could be evaluated. Its result should therefore not depend on the HTTP status code or on the result of a subsequent assertion.

An operation should pass when the engine can construct and execute the interaction sufficiently for subsequent assertions to evaluate it.

An operation should fail when the engine cannot construct or execute the interaction sufficiently for subsequent assertions to be evaluated. This concerns technical execution problems rather than the HTTP status returned by the system under test. Examples include:

a variable used by the operation cannot be resolved;
the request cannot be constructed from the operation definition;
the operation definition is invalid or incomplete;
the connection cannot be established;
the request times out without producing a response that can be evaluated.

Could these pass and fail semantics be added to the Operation Execution section in testing.html?

The defined semantics should subsequently be mapped to TestReport.*.action.operation.result.

TestReport.*.action.operation.result currently permits pass, skip, fail, warning and error. Once pass and fail are related to the TestScript execution rules, it remains unclear when an operation should be reported as warning, skip or error.

In particular, warning is meaningful for some assertions, such as validation that passes with warnings, but there is no equivalent operation use case described in testing.html. Could warning be removed from the allowed operation results if no such use case exists? If skip or error remain distinct from the proposed pass and fail semantics, could their operation-specific meaning also be defined?
