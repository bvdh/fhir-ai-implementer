- **Description**: TestScript.*.action.assert.response represents HTTP response status codes using symbolic values such as okay, created and notFound. Each value maps to a single numeric HTTP status code.

The same expectation can be represented directly using TestScript.*.action.assert.responseCode. For example:

"response": "notFound"

can be represented as:

"responseCode": "404"

The R5 comments already describe response as a shorter way to perform similar verification using responseCode. The current Testing IG retains both representations.

Having two representations for the same HTTP status expectation makes the specification and implementations more complex. Authors must choose between symbolic and numeric representations, while engines must maintain and interpret both. The symbolic code system must also remain aligned with the HTTP status code registry.

A leaner TestScript specification should provide one authoritative representation unless a shorthand covers a distinct testing use case.

Could TestScript.*.action.assert.response be deprecated in favor of responseCode, with examples and guidance using responseCode as the authoritative representation? If response is retained, could its distinct FHIR testing use case be identified?
