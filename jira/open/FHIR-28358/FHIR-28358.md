### 1. Michelle Miller - 2026-09-23

jlyle shared draft language in email
Complex Procedures

Procedures are sometimes composed of smaller sub-procedures. There are three tactics for representing this state of affairs.

If all that is required is a set of named timestamps to specify what steps were taken and when, the Procedure.note element is an Annotation, which has a timestamp.
When these sub-procedures are sufficiently complex to require full representation, they can be represented using Procedure related by the Procedure.partOf reference element. This approach will support arbitrarily complex assemblies of procedure activity, including performer, site, instrumentation, etc.
A middle approach, for cases where some value is needed in addition to the activity name and time (e.g., quantity of fluid resulting from chest tube insertion), such values can be represented as Observations on the Procedure, using Observation.focus.

The fact that there are three patterns for providing procedure composition means that information consumers will need to understand that procedure queries need to include associated Observations (focus = parent process) and Procedures (partOf = parent process). Note that in complex cases, the partOf query may need to be iterative.

### 8. Jose Costa-Teixeira - 2021-04-22

Agree with the key points in the summary above (could not join the call). I share Stephen's approach and I believe it will preserve consistency and non-scattering of information.

The stated requirement can be met by adding a (standard) extension to the procedure that allows one way of doing this: reference to contained resources which only contain information needed - in some cases only minimal information, in other cases more details.

The pattern that Jay (jlyle) seeks - timestamp or references - can simply be achieved by such an extension (a the timestamp is simply a contained resource that contains the timestamp and presumably what the timestamp is about).

That should also support the variations (which seem very difficult to standardize and support with a dedicated attribute):

which timestamps to capture (Anesthesia? Incision? The second incision? Recovery? Transport out of the OR?) - those vary greatly and the standard should not limit that, but harmonize the data.
what level of detail? What codes to be used?

I believe this simple solution works well. I'm not aware of any existing extension that can be used for this.

### 11. Jose Costa-Teixeira - 2020-08-27

In FHIR we don't track (all of) a resource's sub-statuses inside the resource, but by nesting the details. This supports both simple or complex requirements, without contaminating the data with one specific requirement.

Concretely, the Procedure and other resources already have the partOf which allows nesting sub-procedures to contain partial information - which already meets the requirement.

We don't need to make a core change for each specific use case that is already supported - that is a job for profiles.

If we did this change and add just the timestamps for the sub-activities, later we would also need to ask the performers, and the statuses, and sub-sub-statuses - ending up exactly in the resource that we have today. I see no need to downgrade or give a step back.

### 13. Jose Costa-Teixeira - 2020-08-26

Capturing timestamps means capturing sub-status, sub-activities. This can already be done with sub-procedures.

If we were to capture the timestamps, it would hide the hierarchy of sub-procedures: If you have a procedure 1 with sub-procedure 1.1 and 1.2 which has 1.2.1 and 1.2.1, just having the timestamps on the top resource would hide this.

There seems to be a legal requirement to track timestamps. Not to track timestamps in the same resource.

Besides, for any analytical / monitoring applications, I expect that the requirements will extend to also capture the details, which is why we have already the solution in core: a Procedure with sub-procedures is the standard way to do it.

Tracking timestamps throuch contained sub-procedures requires a simple extension or a set of contained resources with 4 or 5 data elements populated, which is a standard and still simple way to solve the local requirement at hand (local= for a specific functionality).
