- **Description**: linkId is the only element that can identify a population — and the spec already treats it as the join key to MeasureReport.group.population.linkId. An optional join key forces every consumer into permanent fallback heuristics (code → criteria name → position) that differ across implementations.

Rationale:

No other element provides identity: population.code is a role, legitimately repeated within a group (ratio measures carry two initial-population entries) and itself 0..1, so a conformant Measure can contain populations with no distinguishing element at all. criteria.expression couples consumers to logic-library internals (renaming an expression becomes a breaking change); element id is tooling-volatile and was not chosen by R5 for this purpose.
Precedent: Questionnaire.item.linkId is 1..1 for exactly this definition/response correlation reason. Measure/MeasureReport is the same pattern; 0..1 here is an internal inconsistency in the spec.
Cost asymmetry: authoring cost is one autogeneratable string per population; optionality costs every evaluator, comparison and certification pipeline a heuristic forever. Implementation experience with multi-group measures (identical population code sets per group) confirms correlation today requires vendor-specific workarounds.
A guaranteed linkId additionally enables: stable population identity across measure versions (trending/diffing), first-class intra-measure references (ratio initial-populations, measure-observation targets) instead of extensions pointing at criteria names, and an enforceable uniqueness/resolvability invariant.

Proposed change: Tighten Measure.group.population.linkId to 1..1 in the base spec (next major release), with an invariant that linkId is unique within the Measure
