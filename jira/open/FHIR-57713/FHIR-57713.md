Update the Choosing an HTTP Method:

Title -> "Choosing a HTTP Method"

From:

As described above, servers that support search via REST SHALL support both the GET and POST methods. However, there are known use cases that prevent one or the other method from being desirable in production. For example, in the case of a large set of Endpoint resources (e.g., FHIR servers), infrastructure could be configured to take advantage of HTTP caching mechanisms that do not function correctly on HTTP POST requests. Conversely, an implementation might not be able to properly secure Personal Health Information (PHI) that appears in request query parameters (e.g., in HTTP logs made by infrastructure) and wants to require the use of HTTP POST for mitigation.

Note that neither GET nor POST have any inherent benefits with respect to security or privacy. The use of various default software configurations in production have led some to believe that POST is more secure because HTTP Body contents are not logged. This is not due to any protocol restrictions and should not be relied on. Implementers should verify that their logging processes adequately protect PHI and other sensitive data.

Given the above considerations, server implementers SHOULD be sure to test both GET and POST search interactions to ensure they are correct on their servers TU. For example, a read-only server may prohibit the HTTP POST verb universally (returning a 405 - Method Not Allowed) and must then ensure correct implementation of HTTP GET.

to:

As described above, servers that support search via REST SHALL support both the GET and POST methods, and MAY support the QUERY method. There are known use cases that favor the various methods, and evaluation and selection are left as implementation decisions. For example, in the case of a large set of Endpoint resources (e.g., directory of FHIR servers), infrastructure could be configured to take advantage of HTTP caching mechanisms that do not function on HTTP POST requests, thereby preferring GET. Conversely, an implementation might not be able to properly secure Personal Health Information (PHI) that appears in request query parameters (e.g., in HTTP logs made by infrastructure) and requires the use of HTTP POST for mitigation.

Note that neither GET nor POST have any inherent benefits with respect to security or privacy. The use of various default software configurations in production have led some to believe that POST is more secure because HTTP Body contents are typically not logged. This is not due to any protocol restrictions and should not be relied on. Implementers should verify that their logging processes adequately protect PHI and other sensitive data.

Given the above considerations, server implementers SHOULD be sure to test GET, POST, and if desired QUERY-based search interactions to ensure they are correct on their servers. For example, a read-only server may prohibit the HTTP POST verb universally (returning a 405 - Method Not Allowed) and must then ensure correct implementation of HTTP GET.

While HTTP QUERY is not yet widely supported, it offers wire-functionality similar to POST while being restricted to GET-impact (e.g., idempotent requests).

- **Change Category**: Enhancement
- **Description**: The HTTP Verb QUERY has been published in RFC 10008.

The FHIR search-type interaction in the search section of the HTTP page should be updated to include the option of using QUERY, alongside GET and POST. Guidance should be updated to prefer QUERY when it is available, though any of the options should be allowed. The mechanism of returning a 405 Not Allowed should cover this as well. The URL should be shaped equivalent to a GET, but have the content equivalent to a POST. Note that the same rules about mixing URI query parameter values and query content values (both are allowed).

The http-verb Code System should have QUERY added.

The Bundle constraints and narrative for Bundle.entry.request.method should be reviewed to ensure QUERY is available where appropriate.

The Operations page should be reviewed to determine if QUERY should be allowed alongside GET in any situations (or if it should be reserved for search only).

The Search page should add HTTP QUERY to the example option styles. It is equivalent to GET for the URL, but equivalent to POST for content. The search page should also reinforce that URLs are returned as GET requests, even if the originating request is a POST or QUERY.

The Messaging page should be reviewed for content that is expecting or expressed as GET to determine if it should be expanded to include QUERY or modified to use FHIR interactions instead of HTTP verbs.

The Exchanging module page should be reviewed to determine if there are places that HTTP verbs are used and whether they should be updated to include QUERY or updated to use FHIR interaction codes.

### 4. Gino Canessa - 2026-06-29

1. We have tried to avoid adding anything more to CapabilityStatement in favor of using Application Features. But yes, we could probably do with proper advertisement instead of just returning Method Not Allowed.

2. The places where we return queries in FHIR are never more sensitive than other content. E.g., while there can be sensitive data in a Bundle's self link, the Bundle entries are chock-full of PHI anyway. Unless there is an unaddressed case that is causing issues, I would lean towards keeping the current mechanism over changing it.

1. The CapabilityStatement

CORS Section

2. Also, RFC 10008 has an explicit model for servers assigning URIs to the query itself or the query result via Location / Content-Location, so FHIR could reference that for large or sensitive searches.
