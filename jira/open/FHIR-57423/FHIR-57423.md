- **Resolution Description**: We will add this to the Boundaries and Relationships section of ServiceRequest:

A ServiceRequest represents what should or should not be performed. Conditions governing when or why the request applies may be represented by Consent, CarePlan, or another appropriate resource and referenced from the request. Other request resources should be used where a more specific resource exists. Intent distinguishes plans and proposals from actionable orders.
- **Change Category**: Clarification
- **Change Impact**: Non-substantive
- **Applied for Version**: R6
- **Description**: ServiceRequest.intent includes code "directive" and is being seen as a way to do patient advance directives (e.g. DNR), that are similar to what Consent allows.

This is a potential clash, and we don't want two ways to do this. That code exists but the directive use is not mentioned in scope and usage, so it is sort of a hidden usage.

Although it is possible to see patient advance directives as "a request to not do this, ever" and technically that is workflow, I don't think this is a good fit for a workflow oriented resource. Some "legal" aspects of the consent/directive will not fit well into a general request pattern, and I just don't think people see consent in the same light as "request for X to be done today"

The overlap with Consent needs to be resolved or at the least documented.

See also
https://jira.hl7.org/browse/FHIR-52914

It is possible that Consent needs more work to cover that use case. There has also been discussion about using ServiceRequest to support the description of what the Consent is about - as supporting information. I don't see why that is needed (a single procedure code in Consent would normally be sufficient, without needing a whole request resource) but even if this is necessary, then it must be clear that is is Consent with support, and that the ServiceRequest is not the consent/directive itself and it must have the Consent "header" to work. Otherwise we have two methods. Core must have one method, and document it clearly, even if other IGs expand on this.

Note that consent advanced directive use case is different from this use case (which also involves ServiceRequest and directives):

Patient is being offered a certain procedure, and they have previously registered a directive to say "never do this" (or possibly "yes ok to do this"), and that check is being recorded. That is a real active ServiceRequest, being allowed/disallowed, and that decision being tracked. That is not the original directive itself, but a workflow that takes account of one, and would record a reference to it.

Also there may be administrative processes around registering consent, and those processes could potentially be managed by ServiceRequests (e.g. please get or check consent), but again those are not the directive itself.

### 3. Lloyd McKenzie - 2026-07-15

This functionality was introduced to support use-cases brought forward by LisaRNelson (I think for PACIO?). The rationale for it existing on Request resources (not just ServiceRequest - most 'order' type resources support this intent) is that only the Request resources allow providing the detailed description of what should or shouldn't happen. Consent wouldn't let you convey medications, dosages, repeat patterns, etc. Also, consent isn't quite the same thing. Consent is "I give permission for y to occur". A directive is "If x occurs, I want/expect you to do y". There might not have been a need for permission to be issued for 'y' at all. The focus instead is on defining what should occur.

We are attempting to clarify the use of these resources. Thoughts on these changes in the narrative text for Consent:

Consent is the appropriate resource for recording a patient's consent or advance directive, including standing instructions to permit or prohibit future care. A ServiceRequest may represent a request for future or ongoing care that is governed by such a directive, or a workflow activity related to obtaining, reviewing, or acting on a consent, but it is not the authoritative record of the consent or directive itself. When a request depends on a consent or advance directive, the relevant Consent should be referenced.
