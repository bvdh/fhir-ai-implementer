FHIR-52810
Signature on Bundle should not use id

Agree to change to cater for the document id to change. Rather than use a magic fragment id, we will use pointer based fragments, since they are unambiguous, and will say to use the fragment identifier '#/'. Update the page rules and worked examples accordingly
|N|No updates in the ballot version, id still used.|

FHIR-52811
The use of # in Provenance in Bundles is unclear
N.A. still unresolved.
N
6.1.2.2.9 says " if the Provenance does not have a target of `Bundle/[id]` it does not represent an embedded signature", so it seems to mean that you need to have 2 targets - one to bundle/id and the other to # - if you want to sign both bundle and the provenance.

FHIR-52813
Countersigning not completely clear

Note that counter-signing signatures will include additional targets, but one of the targets is always `#/')

FHIR-52817
Defining serialization as base64 is inprecise
N.A. still unresolved.
N
According to the discussion with Eric Haas on Jira, it seems I'm misunderstanding at the beginning, they do want to 1st have the signature generated as some JWT format, e.g. , BASE64URL(UTF8(JWS Protected Header)) || '.' ||BASE64URL(JWS Payload) || '.' ||BASE64URL(JWS Signature). and then base64 encode it again. However the it may worth some more explanation here or people will misunderstand like I have. And not sure how to distinguish the different JWT serialization format.

FHIR-52818
Recommend JAdES-B-T for non-repudiation

The Signature MAY conform to JAdES-B-T or any other profiling of JOSE-Signature. If more than integrity is required, the JAdES specification provides a set of profiles, and implementers should consider the rules found in those profiles carefully. For long term signatures, implementers SHOULD conform to JAdES-B-LTA.
