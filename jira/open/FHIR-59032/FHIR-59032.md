- **Resolution Description**: Based on the contents of R4, we cannot force the datatype to not include whitespace as a SHALL. Therefore, change:

A stream of bytes, base64 encoded (RFC 4648). base64Binary content does not include any whitespace or line feeds, but reading applications should ignore whitespace characters (per RFC 4648)

Regex: (?:[A-Za-z0-9+/]{4})*(?:[A-Za-z0-9+/]{2}==|[A-Za-z0-9+/]{3}=)?

There is no specified upper limit to the size of a binary, but systems will have to impose some implementation based limit to the size they support. This should be clearly documented, though there is no computable way for this at this time

to:

A stream of bytes, base64 encoded (RFC 4648). base64Binary content SHOULD NOT include any whitespace or line feeds. Based on RFC 4648, reading applications SHOULD ignore any whitespace characters, and MAY ignore or reject content that includes other non-base-64 characters (e.g., extended characters, etc.).

- **Description**: in R5 and beyond, the description of base64Binary says:

> base64Binary content does not include any whitespace or line feeds, but reading applications should ignore whitespace characters

This language is ambiguous. It's not "base64Binary content SHALL not include any whitespace or line feeds" but nor is it "base64Binary content SHOULD not include any whitespace or line feeds"

It's not clear whether the validator should make it an error or a warning if it doesn't

my opinion: a warning, because this is normative in R4
