- **Specification**: FHIR Core (FHIR)
- **Raised in Version**: R6
- **Work Group**: FHIR Infrastructure
- **Outstanding Negatives**: Normative
- **Related URL**: https://build.fhir.org/search.html#selflink
- **Related Page(s)**: Search
- **Resolution Description**: In the FHIR Core search page, replace the ambiguous introductory use of 'search parameters' with 'parameters' and state that a search-set Bundle self link SHALL contain the recognized query parameters actually used to determine the returned search results or their presentation, including applicable matching parameters and result-control parameters such as _sort, _count, _include, _revinclude, _summary, and _elements.

State separately that a server SHALL NOT synthesize _format solely from the HTTP Accept header; if _format was supplied and used as a query parameter it is retained, while HTTP Content-Type remains authoritative for the representation. Add informative guidance that a client replaying the self URL may still need to send an appropriate Accept header.

- **Description**: Source: https://chat.fhir.org/#narrow/channel/179166-implementers/topic/Self-link.20-.20search.20params.20and.2For.20result.20params.3F

The self link says:
In order to allow the client to be confident about what search parameters were used as criteria by a server, servers...
This intro says "search parameters", but the rest of the section often uses "parameters".

We should clarify whether self links should include only search parameters, or also result parameters.

We should also describe how things like the Accept header should be handled with regard to _format. If a client omits the _format header, but provides an Accept header, should the server move the Accept header value into _format?
