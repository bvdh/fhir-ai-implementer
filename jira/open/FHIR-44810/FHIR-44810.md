Create an example for $validate-code on CodeSystem, and another for $validate-code on ValueSet that demonstrates a concept code that cannot be validated by the server. Use a SNOMED CT expression in the example.

Attendees propose that a warning be issued this way:

OperationOutcome.type = not-supported
- **Description**: When a server validates a complex code - e.g. a grammar - it might not perform all the validation steps that are possible. E.g. tx.fhir.org does not (yet) validate snomed expressions against the MRCM. We should document with an example how to inform the user of what validation limitations they should be aware of, using an issue with a tx-issue-type of ```processing-note``` (see https://chat.fhir.org/#narrow/stream/179166-implementers/topic/The.20URL.20is.20not.20valid.20-.20Snomed-ct.20compositional.20grammar.20.7B.20.7D/near/421727912)

### 9. Daniel Karlsson (Inactive) - 2024-05-28

SNOMED on FHIR meeting 2024-05-28 discussion:

Need to consider both failing and passing validate operations, i.e. result = true and result = false.

A server that has the capability to perform transformations (e.g. from a close-to-user form to classifiable form), that should also be noted. If the server has no or limited capability of transformation, and the MRCM validation fails, that should also be noted.

The levels of expression validation could be:

syntactically correct according to the grammar (SNOMED Compositional Grammar for SNOMED CT)
correct according to concept model (MRCM for SNOMED CT)
correct according to concept model (MRCM for SNOMED CT) AND classifies without inconsistency

Display validation should be mentioned in the documentation.
