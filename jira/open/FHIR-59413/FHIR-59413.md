- **Description**: Summary

Introduce a new HL7 BR&R–owned CodeSystem and ValueSet for Good Clinical Practice (GCP) signature purposes to support unambiguous, machine-readable representation of the meaning/purpose of signatures in GCP-relevant workflows (e.g., informed consent, monitoring sign-off, eligibility approval, RWD attestations).
Current Situation

Today, FHIR uses the ASTM/ISO signature-type ValueSet:

URL: https://hl7.org/fhir/valueset-signature-type.html

Typical usage: Provenance.signature.type carries a code like “Author’s Signature” (urn:iso-astm:E1762-95:2013 / 1.2.840.10065.1.12.1.1).

Example:

{
"resourceType": "Provenance",
"id": "provenanceId",
"recorded": "nowIso",
"agent": [
{
"who": { "reference": "PractitionerRole/highestRoleId" },
"onBehalfOf": { "reference": "Organization/siteId" }
}
],
"target": [{ "reference": "RequestOrchestration/newOrchestrationId" }],
"signature": [
{
"type": [
{
"system": "urn:iso-astm:E1762-95:2013",
"code": "1.2.840.10065.1.12.1.1",
"display": "Author's Signature"
}
],
"when": "nowIso",
"who": { "reference": "PractitionerRole/highestRoleId" },
"onBehalfOf": { "reference": "Organization/siteId" },
"targetFormat": "application/fhir+json"
}
]
}

The current ValueSet:

Collapses many distinct GCP activities (informed consent, CRF review, AE assessment, monitoring sign-off, etc.) into a few generic signature meanings.

Relies on at least one deprecated code system (see FHIR-58852).

Problem / Regulatory Gap

For GCP contexts, this approach does not satisfy 21 CFR 11.50(a)(3):

§11.50(a)(3) requires each electronic signature to clearly indicate its specific meaning (e.g., review, approval, responsibility, authorship).

§11.50(b) requires this information to appear in any human-readable rendition of the signed record.

In practice:

The same generic “Author’s Signature” code is used whether the signer:

Obtained informed consent,
Reviewed and signed off on an eCRF,
Assessed an AE/SAE,
Signed off on monitoring, IP accountability, etc.

This does not clearly indicate the meaning of a specific signature event and therefore does not meet §11.50(a)(3) “as written”.

There is no existing GCP-specific CodeSystem that provides the needed granularity for signature purpose/meaning.

An audit finding has already identified this as a Part 11 compliance issue in a real-world implementation using the ASTM/ISO ValueSet for signature meaning.
Broader Need for a Coded Vocabulary

While §11.50 could theoretically be met using study-specific plain-text labels, there is a broader interoperability and quality need for a standard, coded vocabulary:

1) Machine-driven workflows & validation:Structured, executable study protocols and study configuration increasingly expect signature meaning to be computable, not only legible to humans.

Systems must be able to:

Check that an eligibility-approval signature exists before randomization,
Enforce that required monitoring sign-offs are present,
Configure eCRF locking/approval workflows based on specific attestation types.

Plain text labels are fragile for automated logic (minor wording differences break matching).

2) Secondary use, pooled data, and cross-system consumption: Provenance and signature data stored in FHIR repositories is increasingly reused:

Across studies
Across systems/vendors,
In RWD / external control arm (ECA) work.

For downstream consumers, signature meaning must be identifiable via a stable code in a defined CodeSystem, not by free-text inspection.

3) RWD/ECA under GCP (ICH E6(R3) Annex 2): As of June 2026, ICH E6(R3) Annex 2 (Step 4) and EMA CHMP adoption bring RWD-based designs into mainstream GCP:

Proportionate, risk-based quality management and data governance,
Consent safeguards consistent with E6(R3) wherever RWD is used for outcomes, control arms, or enrichment.

These quality safeguards often require:

Investigator attestations that reviewed data is accurate/complete at each qualifying review,
Attestations for chart abstraction, database locks, and other human/non-human review activities.
These are inherently signature-meaning events and need standard, computable codes.

Proposed Change

Create a new closed, HL7 BR&R–owned CodeSystem and ValueSet for GCP signature purposes and publish it via UTG into THO.

CodeSystem (draft):

URL: http://terminology.hl7.org/CodeSystem/gcp-signature-purpose

Status: draft (initially), content = complete

Owner/Publisher: HL7 International – BR&R Work Group

Scope: Concrete attestation/purpose codes across the GCP trial lifecycle and RWD/ECA signatures.

Illustrative resource skeleton:

{
"resourceType": "CodeSystem",
"id": "gcp-signature-purpose",
"url": "http://terminology.hl7.org/CodeSystem/gcp-signature-purpose",
"version": "0.1.0",
"name": "GCPSignaturePurpose",
"title": "GCP Signature Purpose Codes",
"status": "draft",
"experimental": true,
"publisher": "HL7 International - BR&R Work Group",
"description": "Codes describing the purpose/meaning of signatures in GCP-relevant contexts.",
"content": "complete",
"concept": [
{
"code": "informed-consent-participant-lar",
"display": "Informed Consent (Participant/LAR)",
"definition": "Documents a participant's (or LAR's) voluntary agreement to enter the trial."
}
// Additional concepts as listed below
]
}

A corresponding ValueSet will bind these codes for use in Provenance.signature.type for GCP workflows.
Scope Clarifications

1) “Purpose” vs “Meaning” naming

§11.50(a)(3) speaks in terms of the “meaning” of the signature.
Existing FHIR usage (and ASTM/ETSI vocabularies) frame this as signature “purpose” (reason for signing).
This CodeSystem follows established FHIR naming in this area (“purpose”) while its codes exist specifically to ensure that §11.50 “meaning” is captured explicitly and unambiguously.

2) Relationship to other FHIR status codes

Other FHIR resources already have status code systems (e.g., ResearchSubject.status, ResearchStudy.status).

Those describe the state of a resource (on-study, withdrawn, active, closed, etc.).
The proposed CodeSystem describes the reason for a specific signature event at a specific point in time.
Signatures must not be inferred from status transitions. Under §11.50, the signed record itself must carry the explicit meaning of each signature.

Therefore, this CodeSystem:

Does not derive from or bind to status code systems,
Co-exists with them: status codes record state, signature-purpose codes record attestation meaning.

Proposed Concept List (Initial Set)

The following codes are proposed as the initial, closed set for the GCP signature-purpose CodeSystem:

Informed Consent (Participant/LAR) — informed-consent-participant-lar
Documents a participant’s (or LAR’s) voluntary agreement to enter the trial.
Informed Consent Discussion Conducted By — informed-consent-discussion-conducted-by
Identifies who conducted the consent discussion and confirms it met GCP requirements.
Impartial Witness Attestation (Informed Consent) — informed-consent-impartial-witness
Confirms an impartial witness observed consent where the participant/LAR cannot read.
Re-consent to Amended Informed Consent — informed-consent-reconsent-amendment
Documents agreement to a revised ICF issued mid-trial.
Withdrawal of Consent Attestation — informed-consent-withdrawal
Documents a participant’s decision to withdraw consent to further participation.
Statement/Agreement of Investigator — statement-of-investigator-agreement
Investigator’s formal commitment to conduct the trial per protocol, GCP, and law.
Delegation of Authority Log Approval — delegation-of-authority-approval
PI’s approval of the site’s task-delegation log.
Protocol / Protocol Amendment Approval — protocol-amendment-approval
Approves a protocol or amendment prior to implementation at a site.
Source Data Verification (SDV) — source-data-verification
Confirms specific eCRF data points match the original source documents.
Monitoring Visit Sign-Off — monitoring-visit-sign-off
Confirms a required monitoring visit was completed as documented.
Query Clearance / Resolution — query-clearance-resolution
Confirms a data query has been resolved and the resolution accepted as final.
Investigator eCRF Data Accuracy Sign-Off — investigator-ecrf-data-accuracy-sign-off
Investigator’s attestation that the eCRF data for a specific visit or form is accurate and complete.
Investigator Protocol Deviation Acknowledgment — investigator-protocol-deviation-acknowledgment
Investigator’s formal acknowledgment of a documented protocol deviation record.
Investigator Final Subject Sign-Off — investigator-final-subject-sign-off
Investigator’s final, holistic sign-off on the complete subject eCRF record.
Medical Assessment / Review (AE/SAE) — medical-assessment-review
Clinician’s medical judgment recorded on a reported adverse event.
Eligibility Approval — eligibility-approval
Certifies a subject meets the protocol’s eligibility criteria.
Data Entry / Authorship — data-entry-authorship
Identifies who originated or transcribed the recorded data.
Data Correction / Amendment — data-correction-amendment
Identifies who is responsible for a correction to previously entered data.
Data Review / Cleaning Sign-Off — data-review-cleaning-sign-off
Data manager’s review of data for completeness and protocol conformance.
eCRF Freeze / Lock Approval — ecrf-freeze-lock-approval
Approves locking a form, visit, or dataset from further routine edits.
Attestation of Truthfulness (ePRO/eCOA) — attestation-of-truthfulness
Participant or caregiver attests that entered outcome data is true and accurate.
Investigational Product Accountability / Reconciliation — ip-accountability-reconciliation
Confirms IP accountability records are accurate and reconciled.
Investigational Product Dispensing / Administration — ip-dispensing-administration
Confirms IP was dispensed or administered to the participant per protocol.
Randomization Confirmation — randomization-confirmation
Confirms a participant was randomized using the protocol-defined procedure.
Emergency Unblinding / Code Break Attestation — unblinding-emergency-code-break
Documents an emergency unblinding event and its medical justification.
SAE / Expedited Safety Report Approval — sae-expedited-report-approval
Approves an expedited safety report for regulatory/IRB submission.
DSMB / DMC Recommendation Sign-Off — dsmb-recommendation-sign-off
Confirms an independent data monitoring committee’s review and recommendation.
Audit / Inspection Finding CAPA Acknowledgment — audit-capa-acknowledgment
Confirms acknowledgment of an audit or inspection finding and its CAPA plan.
Chart Abstraction Attestation — chart-abstraction-attestation
Abstractor attests correct transcription from a source chart into the RWD extract.
Source System Extraction Attestation — source-extraction-attestation
Attests that an RWD extract accurately reflects the source system at extraction time.
Data Curation / Steward Certification — data-curation-certification
Data steward certifies a curated RWD dataset meets quality and fitness-for-use criteria.
Algorithmic Derivation Attestation — algorithmic-derivation-attestation
Documents that a data element was derived by an algorithm, not directly observed or entered.
Data Partner / Contributing Institution Certification — data-partner-certification
Contributing institution certifies the provenance and integrity of its RWD contribution.
