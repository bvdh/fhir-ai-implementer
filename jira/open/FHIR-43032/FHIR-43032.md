- **Description**: When defining a profile, we want to link it to the Logical Map that represents it.

The detailed mapping - at element level - between the LM and profile can be established with ConceptMap,

This request is for a simple indication that "this profile implements logical model X" This could be expressed by either/any of:

a new extension on the profile
a ConceptMap (mapping the top elements)
mapping inside the resource metadata

If the preferred approach is a ConceptMap, this may be interesting to document in the logical models page.

If the preferred approach is an extension, one should be defined.

### 7. Alexander Henket - 2024-05-20

We have looked at various ways to do this years ago and settled for mappings inside the profile. The downside is that updates to that mapping, constitute a change in the profile. This is fine if the profile is ours, but a bit of a waste when the profile is not, e.g. IPS. We will then create a profile on top of that external profile for the purposes of adding those mappings.

Having something outside of the profile that merely points to the profile, was considered but how to then offer implementers a view on how these separate artifacts relate was unsolvable back in the day. Having the mapping and the profile version independently would be a good thing.

Having a derived profile that only lists the mappings, is somewhat the same as what the proposed ConceptMap would do, would it not? The added benefit is that you'll have more context and validation than possible with a ConceptMap.

### 10. Jose Costa-Teixeira - 2024-04-29

One way to express this is "StructureDefinition B realizes/implements StructureDefinition A".

I'd like to use this for

documentation (in the IG, show that Profile B implements logical model A
traceability (across IGs, finding which profiles will need to change if we change a logical model).
fancy diagrams?
I have no preference between mapping, extension and conceptmap. I guess tooling would drive this the right way - what is the best if the LM is in package A and the profile is in package B? Maybe an Extension? What makes it easier for the tooling to pick up?

Arguments are the obvious ones:

extension is visible and easy to author currently
conceptmap requires a new resource (or reusing the conceptmap for the element mapping - note that element mapping may not be done always with a conceptmap)
conceptmap does allow richer expression of what is the relationship (currently I have no need for that, but not sure if we want to constrain our metadata or have it richer)
Mapping in the resource, as we do for the Patterns in the core spec - Could work f tooling understands it and can use it across IGs.

Whatever is the mechanism, it should be easy to use in an IG. The profile page for an IG should be able to capture this.

Not sure if other resources would have the same relationship. This starts with profiles to models. Is there such a relationship "implements" between a data element and a concept in a CS? maybe not, but I am not sure how generic this problem is.
