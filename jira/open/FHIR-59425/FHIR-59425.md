Claude on FHIR-46191: linkId whitespace rule in Questionnaire and QuestionnaireResponse

que-16 and qrs-3 don't enforce the rule. Both use $this.matches('[^\\s]( [^\\s])') with no anchors. FHIRPath matches() succeeds on a match anywhere in the string (the Java engine uses find()), so " a", "a ", "a b" and "a\tb" all pass. Only empty or all-whitespace strings fail. Fix: anchor the pattern as '^[^\\s]( [^\\s])$', or use matchesFull() where engines support it.

The build silently drops the regex extension on Questionnaire.item.linkId. Kindling's ResourceParser.parseED reads it into ElementDefn.regex, but ProfileGenerator.defineElement never writes it back. Kindling only emits the regex extension for primitive datatype definitions. The extension is missing from both the snapshot and the differential of the published profile. This is a general kindling bug: any element-level regex on a core resource element is lost.

Only Questionnaire has the extension. QuestionnaireResponse.item.linkId got qrs-3 but no extension, and the ticket's implementation comment mentions only the constraint. Either remove the extension from Questionnaire, or add it to both once kindling emits it.

The existing Questionnaire.item.linkId comment contradicts the rule. It still says "LinkIds can have whitespaces and slashes by design," which reads as permitting what que-16 is meant to forbid. Suggested rewording: single internal spaces and slashes are allowed; leading, trailing, repeated or non-space whitespace is not.

Typo: the human text of both que-16 and qrs-3 says "intevening."
