- **Description**: There is conflicting information in the FHIR spec on whether it is within FHIR's scope to impose user interface, workflow, or clinical best practices.

Examples 1 (against UI and workflow scope)

The FHIR spec states that user interface and workflow guidance is outside the scope of FHIR:

FHIR Overview - Clinicians
The FHIR specification does not attempt to define good or best clinical practices, nor does it provide guidance on user interfaces or workflows. Guidance in these areas may be useful, but it is outside of FHIR's scope.
Example 2 (for UI and workflow scope){}

The Obligations page deviates from that stance:

Obligations
Implementation guides that describe specific implementation solutions and application roles are also concerned with application behavior - what information must be provided under what conditions, and setting expectations for how particular data elements are handled.
The paragraph on it's own doesn't quite stray into problematic territory, but then the Obligations value set includes codes for SHALL:user-input, SHALL:display. Those are technically in the extensions IG, but given that the Obligations page is in the core spec, I think we should treat all of Obligations as "core spec relevant" for resolving this issue.

Example 3 (for UI and workflow scope){}

Also, the Additional Bindings Purpose value set includes codes that allow violating that stance (e.g., ui, best-practice). 'ui' is the primary problem code. 'best-practice' can be applied in a way that is not about clinical best practices, but in some cases, it could influence clinical best practice.

Example 4 (implicitly for UI and workflow scope){}

There are FHIR IGs in the wild that impose UI or workflow requirements (e.g., Da Vinci CRD/DTR). I'll try to do some more homework and drop more examples in the comments.

Background Discussion

There is this zulip thread about whether that approach can be successful: https://chat.fhir.org/#narrow/channel/179166-implementers/topic/FHIR.20IGs.20with.20non-interop.20conformance.20statements

Summary

The FHIR spec should have a consistent, and well-vetted (by implementers and end users) stance on whether the FHIR spec is an appropriate vehicle for imposing user interface and workflow requirements on end users. This is a major issue that should involve convening a broader range of stakeholders than I expect are usually attending WG calls.

Recommendation:

Remove "user-input" and "display" codes from the Obligations value set. (technically an extensions IG change, but because of the explicitl link from the obligations page (via the extension definition), I think it counts as a ballot-driven change).
Remove the "ui" and "best-practice" codes from the Additional Binding value set.
Provide guidance to IG authors that FHIR IGs should be focused on data exchange, not defining user interfaces or end user workflow. I'm open to the best place to put this guidance.

Reasons for the recommendation:

I'm not aware of any other interop standard that has successfully imposed user interface and workflow requirements in a data exchange specification, and I'm confident that if FHIR attempts it, it will only lead to missed expectations (especially over time, as UIs evolve and improve, and FHIR version advancement is slower or stops). My recommendation is to align the FHIR specification (obligations and additional bindings) with the approach we outline in the clinician's overview, where UI and workflow are explicitly out of scope for FHIR.

Specifically:

FHIR spec authors are experts on data interoperability. They are often not experts on user interfaces or workflows.
Similarly, the FHIR implementer community involved in reviewing and voting on FHIR specifications is composed of implementer experts on data exchange. FHIR (to my knowledge) does not actively solicit input from user interface or workflow design experts. We all have opinions about this, but are not the experts on it.
Real-world systems very often must support multiple standards at once. This may be different core standards, like NCPDP, HL7v2, FHIR, etc., or it could be different FHIR IGs. If different standards have conflicting guidance for UI or workflow, then implementer systems are stuck. If different standards have non-conflicting, but additive requirements, then user interfaces and workflows would become frustrating and burdensome for end users.
User interface and workflow design is a very iterative process that involves gathering ongoing feedback from end users. App developers can iterate and innovate as fast as their product lifecycle allows. However, if these requirements are enshrined in FHIR specifications, that iteration (and innovation) becomes much slower.

If the broader implementer community does determine that imposing user interface, workflow and best practice requirements is within FHIR's scope, then we should say that on the Clinician's overview, and clearly highlight all the risks and concerns inherent in that approach.

## Comments

### 1. Lloyd McKenzie - 2026-07-20

The core specification doesn't make assertions about UI or any particular business flow. IGs, on the other hand, are about defining interoperability and implementation expectations in a specific context. Depending on the intent of the IG,

Framed another way, any party authoring a spec is allowed to define whatever requirements it likes on implementations that want to for an implementation to claim conformance to the spec. If someone wanted to, they could set requirements for the names of variables in software written to comply with the specification.

FHIR is intended as a generic framework for creating specifications. As a generic framework, it needs to support whatever specification authors want to say - and some specification authors absolutely want to set expectations for internal software behavior. Whether this is always appropriate varies, but there certainly are situations where defining expectations for UI behavior, persistence, internal processing, and other "non-over-the-wire" functions are essential to ensure that systems that claim conformance meet the requirements of the entity authoring the specification.

I'm totally on board with highlighting the risks and considerations involved when specifications tread into internal system behavior. And the Obligation extension documentation should be updated to point to this section.
