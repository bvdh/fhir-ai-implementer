## Comments

### 1. Lloyd McKenzie - 2026-06-11

There are edge cases where the replacing order gets created, but the instructions are "finish what you're doing, then switch". It's still a replacement order. And it still doesn't come into effect until the old order is completed or stopped. That's the standard implementation behavior. It's totally consistent. If the order was stopped before the replacement was created, the order is effective now. If it's not yet stopped/completed, then you need to wait until it is stopped/completed. If you have a business arrangement that leads you to be the one to stop the prior order, you can do that - just as you can satisfy any other business arrangement. But no such arrangement is implicit in the existence of the replaces relationship.

You're correct that there are multiple ways to represent the business scenario described. The same is true of a variety of orders. Someone can adjust a prescription for warfarin to change the dose, or they can cancel the old and create a new one. Which approach is done is driven by regulatory policy, organizational policy, and/or clinician's convention. But FHIR definitely doesn't dictate. And if you're building a system that spans regulations/organizations/providers with different approaches, your software will need to handle both - and possibly be configurable to force one or the other for a given implementation.

relatesTo is a horrible thing on DocumentReference too. It's an anti-pattern in FHIR. everything relates to everything. You ate dinner 6.25 hours after I had a haircut. Those two acts are therefore related. Such an element invariably gets interpreted as "these things are related in the way my organization agrees is important/relevant" and that's not going to be consistent with how any other organization is going to interpret the element, which makes it patently unsafe.

It's not quite so bad in CDA, as all it's really saying is "here's a bunch of stuff I wanted to include, but can't be bothered figuring out the semantic relationship, but that doesn't matter because a human being will read it and understand and I have no need for the computer to understand anyhow". That's definitely not what's happening in this usecase. (And it's not what's happening with DocumentReference either, because there's no 'packaging for a human to see' implicit in that resource.)

### 2. Vassil Peytchev - 2026-06-10

The current definition of Request.replaces states: "Completed or terminated request(s) whose function is taken by this new title." It is hard for me to understand how this can be interpreted as anything different than a requirement for the original Request to be completed or terminated.

As far as I can tell, the additional use case here is extending the orignal request. I think that changing the meaning of Request.replaces to handle that is fraught with problems. For example, there would be multiple ways to represent a ServiceRequest for 5 physical therapy sessions being extended to 10 sessions aftger the 3rd session:

The original service request is marked as completed/terminated, and a new service request is created with 7 sessions
The original service request is left active, and a new service request is created with 5 sessions

If both of the above cases are represented with a single Request.replaces element, I believe this becomes a burden for implementers, as they always have to anticipate varying interpretations of the .replaces element. If, instead, the first case uses the Request.replaces element, and the second uses a hypothetical Request.extends element, the implenation would be much simpler.

I am not sure why the approach of using a relatesTo element as it is defined for DocumentReference is not appropriate for Request. The clear semanitcs for the use of releatesTo have been used since the approval of the CDA. If it is considered too broad, I think all the use cases that we currently have can be met with Request.replaces maintaining the requriement that the original is completed/terminated, and adding a new element or FHIR extension for Request.extends where there is no assumption that the original is completed/terminated, btu the semanitcs of "in addition to" is clear.

### 3. Lloyd McKenzie - 2026-06-08

We definitely don't want to change this to 'relatesTo', as that's a generic assertion that could be true of any reference element. It's not clear how the change to the ServiceRequest definition is in any way inconsistent with the original intention. 'replaces' was always intended for things like a 'renewal' prescription. Whether or not it invalidates the previous order varies by business practice. It's certainly possible that the creation of a Request with a 'replaces' could trigger the stopping of the prior Request, but there was never a requirement that this occur. The definition actually implied that the transition of the target Request needed to happen first. The use-case raised in FHIR-54876 is a completely reasonable use of this element and it would be problematic to have to have a completely new relationship for "replaces once the target is ended".

What we could do is clarify "If the target resource is not already in an 'ended' state, the creation of the 'replacing' resource cannot be presumed to automatically transition the target resource into an ended state. However, implementations MAY choose to agree to such a workflow shortcut if that meets the requirements of their implementation community."

We want to hear from vassil before we vote on this however.
