- **Description**: A DeviceMetric describes the capability of a device to generate certain types of observations. The current text in Device suggests that these are dynamic:
DeviceMetric - Describes a measurement, calculation or setting capability of a device instance. A Device may include multiple device metrics, each yielding a different observation. The DeviceMetric models the properties of the Observations generated by and/or about the device such as whether or not the Observation is a setting. A DeviceMetric describes aspects of the device that may change over time.
The capability of a device of being able to produce certain types of observations such as MDC_PULS_OXIM_SAT_O2 is typically static. Most other element of DeviceMetric are also static.

The DeviceDefinition resource contains such static aspect of a Device model and it would be logical to include the static data of DeviceMetric as well, e.g. by allowing DeviceMetric to refer to a DeviceDefinition instead of to a Device..

### 13. Erik Moll - 2025-11-19

I derived an ObservationDefinition resource from a DeviceMetric example in the PHD IG and this works fine, except for the measurement frequency. This is present as an attribute in the DeviceMetric, but absent in ObservationDefinition. Since the measurement frequency is a dynamic aspect, this should be modelled using a DeviceMetric instance if desired. So, IMHO no changes needed to ObservationDefinition.

The example can be included in the FHIR R6 core specification.

I also noted that DeviceMetric does not support compound observations such as a non-invasive blood pressure measurement with a diastolic and systolic numeric component, whereas ObservationDefinition does support components. Going back to the 11073 standards I learned that metrics are indeed not intended to represent compound measurements; e.g., for blood pressure there would be one metric that represents just the measured blood pressure signal and systolic and diastolic pressure would be derived from this signal. Note that the binding of DeviceMetric.type is to Device Metric and Component Types (Preferred) - explicitly targeting components, which confirms this thinking.

However, nothing prevents the use of a DeviceMetric resource for a (compound) blood pressure measurement to capture the (current) measurement frequency. No changes needed.

### 15. Erik Moll - 2025-11-11

After some further thinking and checking the resource types that we already have, a set of ObservationDefinition resources can be used to model the (static) set of observation types that a (type of) health sensor device can produce. We do not need two ways to do this and as indicated using DeviceMetric would not be a good fit, since that is targeting the dynamic aspects of the generation of observations, such as settings, calibration, operational status, by a device instance.

My proposal would be to make no changes to DeviceMetric - leave this as is.

For the PHD IG I'll consider using ObservationDefinition instead of DeviceMetric to represent the set of supported Observation types as reported by a PHD.
