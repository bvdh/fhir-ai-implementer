- **Specification**: FHIR Core (FHIR)
- **Raised in Version**: R6
- **Work Group**: Security
- **Outstanding Negatives**: Normative
- **Related Page(s)**: Security Labels
- **Description**: >The intent of a security label is that the recipient of resources or bundles with security-tags is obligated to ... carry the security labels forward as appropriate.

Very common interop scenario is – Provider org queries/receives information from a trusted external system that a patient has X problem on their problem list. That information is not automatically added to the patient's chart. Rather, during the next clinical encounter with the patient, a clinician reviews this problem, discusses it with the patient/confirms it, and adds it to the provider's local version of that patient's problem list.

Later, the provider org is queried for the patient's problem list. Do any security labels present from the initial data exchange with the trusted external system apply? For example, DELAU wouldn't make sense for treatment, and HIPAA governs NOREUSE and impacts purpose of use as well.

For many labels (e.g. restrictive), the appropriate action would be for the clinician to not only confirm the condition, but also the label.

Ultimately, how do security labels interact with care delivery? If the page even just provided some example realworld scenarios, it would help the reader.

## Comments

### 1. John Moehrke - 2026-08-31

Good discussion. The text on the security labels page is intended to be informative, not normative. The expectation is that there will be regional policy, possibly Implementation Guides, that apply normative actions to the given codes. Thus the sentence identified here is intended to indicate the potential. If the sender does include DELAU, that is a signal that the sender can only provide a copy of the data and is not authorized to allow the recipient to persist. If that policy is not acceptable at the recipient. I would expect that this would not happen in environments where the recipient is unaware and unwilling to abide by the given obligation or refrain codes; but in an environment where there is policy agreement to abide by a given set of obligation or refrain codes then the recipient is expected to abide by the code; and not doing so would mean a breach of policy. You can see that this is all founded in a trust framework, something that the FHIR core does not define.
