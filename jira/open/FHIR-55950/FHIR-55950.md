# FHIR-55950: Please change DxReport.comparison from generic List to Backbone with it's own type and binding to list of relationship types

- **Description**: The data model of the new DxReport.comparison Reference(List) is too abstract. The additional layer of indirection increases complexity and optionality and therefore reduces interop. The .comparison element is more specific than .supportingInfo, and should be more tightly restrained in it's references.

We understand and appreciate the goal of maximizing flexibility for future IG authors towards the goal of taking this resource normative this year.

Resulting from discussion in the InM FHIRcast WG calls, we ask that the data type of .comparison be modified to mirror that of .supportingInfo. It should be a Backbone element, with a mandatory relationship type, and a reference to definitely Observation, ImagingStudy, Procedure and DiagnosticReport ... perhaps a few others.

In the FHIRcast call we brainstormed some types of relationships that should go into this newly proposed valueset –

Types of comparisons:

Comparison of discrete findings via Observation (e.g. white blood cell count for tb patient, dimensions/volume of tumor size)
Prior studies referenced by the clinician while creating the report (via ImagingStudy, or DiagnosticReport)
...

## Comments

### 1. David Barwin - 2026-09-23

One option would be taking the necessary concepts from List.entry and promoting them into the backbone, or even defining a common data type with this structure.

The revised structure might look like:

comparison 0..*
type 0..1 CodeableConcept
reference 0..1 Reference(ImagingStudy | DiagnosticReport | Observation)
emptyReason 0..1 CodeableConcept

with an invariant along the lines of: reference.exists() xor emptyReason.exists()

### 2. KevinO'Donnell - 2026-08-11

The driving need for explicit comparison data was a to have set of comparison references and an emptyReason. List provided that off the shelf so we didn't re-invent it. Hypothetically, we could have a backbone containing a 0..* Reference element and an emptyReason element.

Since the List is a snapshot, it might make some sense to include it inline rather than as a standalone List instance.

As David notes, the element can be profiled down. The Imaging Diagnostic Report IG constrains it to ImagingStudy and DiagnosticReport. The comparison DiagnosticReport would be the source of granular access to Observations so they are not referenced directly.
