- **Description**: ResearchStudy provides three overlapping mechanisms for representing names or titles:

ResearchStudy.name: a computer-friendly name
ResearchStudy.title: a human-readable title
ResearchStudy.label: additional names classified using ResearchStudy.label.type and ResearchStudy.label.language

The intended relationship between these elements is unclear. In particular, the TitleType codes `primary`, `human-use`, and `machine-use` appear to overlap with ResearchStudy.title and ResearchStudy.name. The specification does not define whether equivalent values should also be repeated in ResearchStudy.label, which element takes precedence if the values differ, or how a consumer should select the preferred display title.

The TitleType terminology also combines several independent classification dimensions:

`official`, `scientific`, `plain-language`, `short-title`, etc. describe the purpose or form of a title.
`language` describes a language variant.
`autotranslated` describes how a title was produced.
`human-use` and `machine-use` describe the intended consumer.

ResearchStudy.label.type has cardinality 0..1 and is a CodeableConcept. Multiple Coding repetitions within a CodeableConcept should normally represent equivalent concepts in different code systems, not a conjunction of independent classifications. It is therefore not possible to state cleanly that a title is, for example, both official and scientific.

The `language` code appears particularly redundant now that ResearchStudy.label.language explicitly records the language. For example, English and German scientific titles can be represented as separate label repetitions with `type = scientific` and the appropriate `language`. Assigning `type = language` instead loses the information that both are scientific titles.

Similarly, `autotranslated` represents translation provenance rather than a title type and cannot be combined cleanly with `official`, `scientific`, or another functional title type. This information may be better represented separately from the title classification.

Please consider:

1. Clarifying the distinct roles of ResearchStudy.name, ResearchStudy.title and ResearchStudy.label, including precedence and whether values should be duplicated.
2. Retaining name and title as the designated computational name and default human-readable title, while defining label as representing alternative titles.
3. Providing a ResearchStudy-specific value set that excludes title types which duplicate the dedicated elements or represent orthogonal properties.
4. Removing `language` from the applicable ResearchStudy title types because language is already represented by ResearchStudy.label.language.
5. Representing automatic translation as a separate property or extension rather than as a mutually exclusive title type.
6. Clarifying whether `plain-language` means a title written in plain language or a public/lay title; `public title` or `lay title` may be clearer for research-study registries.
7. Requiring ResearchStudy.label.value when a label repetition is present. Its current cardinality of 0..1 permits an empty label.
8. Adding guidance on when to use repeated ResearchStudy.label elements and when to use the standard translation extension on ResearchStudy.label.value.

## Comments

### 1. BrianAlper - 2026-10-15

The confusion regarding .title, .name, and .label appears to come from two different pathways for derivation of these elements. The title and name elements (with human-use title and machine-use name) match FHIR structures used for many other Resources (e.g. Evidence, EvidenceVariable, PlanDefinition, ActivityDefinition) where the title and name are for the Resource instance as the content of the resource does not typically have a title or name. The label element is designed for a research study which may have any number of labels (or titles or names), and the modeling of this concept (multiple labels for the knowledge object described in the resource) is represented in Citation.citedArtifact.title (https://hl7.org/fhir/6.0.0-ballot1/citation.html).

Suggestions for how to handle for ResearchStudy (derived from the 8 concepts for consideration) include:

Change the short/definition for ResearchStudy.title and ResearchStudy.name to make it clear these elements are metadata about the Resource itself, used for finding the Resource instance.
Modify the ResearchStudy.label.type from 0..1 to 0..* (breaking change, but more practical and matching the Citation.citedArtifact.title pattern)
Modify the ResearchStudy.label.value from 0..1 to 1..1 (breaking change, but a label is useless without a value)
Modify ResearchStudy.label to be isSummary (as the title of the research study would be useful to share in a summary of the resource)
Remove 'language' from the TitleType value set (it was there preceding the availability of a separate language element to specify the language)
Review the TitleType value set for other changes to improve definitions, but consider this in coordination with the EBMonFHIR project so the same value set can be used for ResearchStudy and Citation (which is renamed PublicationRecord)
