There doesn't appear to be any discussion of how the fhirVersion element of IGs, StructureDefinition, and requirement type CapabilityStatement fhirVersions should be used. (Or how the resource itself can be of a different version than the fhirVersion it specifies.) http://build.fhir.org/versioning is about identifying (or specifying) system or resource FHIR version; http://build.fhir.org/versions.html is primarily about managing spec versions. (E.g., there should be a discussion of what system or resource FHIR versions a IG, SD, or requirement-type CapabilityStatement with a given fhirVersion is compatible with. Is a 4.1.0 SD compatible with a 4.0.1, 4.1.1, or 4.6.0 system?) This discussion should be on a common page (to prevent different rules for different resources), but linked from each of the above resources.

<a name="conformance-version"> </a>
<h2>The FHIR Version of Conformance Resources</h2>

<p>
Several conformance resources — <a href="capabilitystatement.html">CapabilityStatement</a>,
<a href="structuredefinition.html">StructureDefinition</a> and
<a href="implementationguide.html">ImplementationGuide</a> — carry a <code>fhirVersion</code>
element. This element does <b>not</b> state the version of FHIR that the resource itself is written
in. It states the version of FHIR that the resource's <i>content</i> applies to: the version of the
structures that a StructureDefinition constrains, the version of FHIR that a CapabilityStatement
describes a system for, or the version(s) that an ImplementationGuide is written against.
</p>

<p>
There are therefore two versions in play for any one of these resources — the version the
resource is itself expressed in, and the version its <code>fhirVersion</code> element declares
— and they are independent of each other. They may be the same, but they need not be.
</p>

<h3>Why the two versions can differ</h3>

<p>
It is possible, and increasingly common, to use a conformance resource expressed in one version of
FHIR to describe content or services in a <i>different</i> version. The resource is serialized using
the definitions of whichever release a system uses internally, while its <code>fhirVersion</code>
records the version that the content actually pertains to. The element paths, type names and resource
names <i>inside</i> the resource are those of the declared <code>fhirVersion</code>, not of the
version the resource is serialized in. This works because the structure of these conformance
resources is itself stable enough across versions to carry content that describes another version.
</p>

<p>For example:</p>
<ul>
<li>
The FHIR validator and the IG publisher work entirely with R5 resources internally, but can
validate — and emit conformance resources for — content in any version. A
StructureDefinition they produce may be an R5 resource whose <code>fhirVersion</code> is
<code>4.0.1</code>: an R5 resource that constrains R4 content.
</li>
<li>
As cross-version implementation between R4 and R6 becomes common, registries and IGs will
routinely hold and exchange conformance resources whose <code>fhirVersion</code> names another
version.
</li>
</ul>

<p>
When first encountered this is counter-intuitive, but it is a deliberate and well-established
pattern. A consumer should always read the <code>fhirVersion</code> element to determine which
version of FHIR the content describes, and interpret the resource's paths and type references
against <i>that</i> version — regardless of the version in which the resource itself was
received.
</p>

<h3>Notes for each resource</h3>

<p>
<b>StructureDefinition</b>: <code>fhirVersion</code> is the version of FHIR whose structures the
StructureDefinition defines or constrains. The element paths and types in its differential and
snapshot are those of that version.
</p>

<p>
<b>CapabilityStatement</b>: <code>fhirVersion</code> is the version of FHIR that the described system
operates in — the version of the resources, interactions and search parameters that the
statement refers to. This applies equally to capability statements that state <i>requirements</i> or
desired capabilities and to those that describe a specific running system.
</p>

<p>
<b>ImplementationGuide</b>: unlike the others, <code>fhirVersion</code> on ImplementationGuide is
<code>0..*</code> — an implementation guide may list <i>several</i> versions, to declare the
versions it can be used with.
</p>

<blockquote class="stu-note">
<p>
<b>Implementation note:</b> although ImplementationGuide allows multiple <code>fhirVersion</code>
values, there is — at the time of this publication — no tooling that produces or consumes
implementation guides spanning multiple FHIR versions. Multi-version implementation guides are
therefore an unrealized capability: in current practice an implementation guide declares the single
version it was built against.
</p>
</blockquote>

<p>
The rules on this page apply uniformly to every conformance resource that carries a
<code>fhirVersion</code> element. The CapabilityStatement, StructureDefinition and ImplementationGuide
pages link here rather than restating the rules, so that there is a single, common set of rules for
all of them.
</p>
