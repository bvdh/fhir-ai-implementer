- **Description**: Proposal: Broaden the definition of the Requirements.statement.reference element (and the corresponding validation guidance) so that it explicitly permits a relative reference to source material within the same publication — for example, a page or anchor within an Implementation Guide such as general-guidance.html#section.

Background / problem

The Requirements.statement.reference (type url, cardinality 0..*) currently carries the short definition: "External artifact (rule/document etc. that) created this requirement."

The word "External" combined with the url datatype's expectation of an absolute, externally resolvable address causes the FHIR validator / IG Publisher to flag relative values such as foo.html#general-guidance (warning/error), even though that link is the intended traceability target and resolves correctly in the rendered IG.TT

Rationale

The Requirements resource's primary stated use case is formal requirements tracing for specifications published as Implementation Guides. Referencing the IG's own narrative is core, expected usage — not an edge case.

Requested changes

Reword the element's short/definition to remove the implication that the target must be external, e.g. short becomes "Artifact (rule/document etc.) that is the source of this requirement."
Add a comment clarifying that the value MAY be a relative URL that resolves within the same publication context (e.g. a page or anchor within the same IG), and need not be absolute or externally resolvable.
Update the corresponding validator / IG Publisher guidance so that a relative reference on this element does not raise a warning or error.
Consider applying the same clarification to Requirements.statement.satisfiedBy, which shares the URL data type and the identical relative-reference scenario.
