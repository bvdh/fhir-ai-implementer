# FHIR-53711: Endpoint.connectionType is insufficient

- **Status**: Resolved - change required
- **Project**: FHIR Specification Feedback

- **Specification**: FHIR Core (FHIR)

- **Related Artifact(s)**: EndPoint
- **Grouping**: Extension
- **Resolution Description**: We will create a new extension (based on the NDH ext-implementation-guide extension).

Name: endpoint-feature

The structure will be based on : https://build.fhir.org/ig/HL7/fhir-us-ndh/en/StructureDefinition-base-ext-implementation-guide.html with the following differences:

The ig-usecase will be a string data type, instead of CodeableConcept.
Any textual references to NDH will be removed.
The extension context will be Endpoint or Endpoint.payload - so can be generic across all payloads, or for a specific payload)
- **Resolution Vote**: Brian Postlethwaite / John Moehrke : 10-0-0
- **Vote Date**: 2026-09-21
- **Change Category**: Enhancement
- **Change Impact**: Non-substantive
- **Description**: Today Endpoint has one codeableConcept for the .connectionType. This element is not sufficient to indicate an Implementation Guide + the Actor within that implementation guide + the options within that implementation guide. Even for non-IHE IGs, there are at least two actors (client vs server), but many IGs have multiple Actors.

The solution today is either (a) define lots of codes representing the triplet (see IHE-mCSD), or (b) define a new extension to carry the detail (see NDH)

Best would allow

canonical URI or CodeableConcept
Version
Actor
Options

Why adding a link to an implementationguide (1..1?) deliberately pointing to a publication that may contain several actors? why not just the canonical of the actorDefinition? Wouldn't that solve the actor and version?
Did you consider CapabilityStatement, which seems more the resource for such technical definitions? I don't have the understanding that CapStatement represent an entire system. the approach "actor options" should be normalized. IHE calls it actor options but it is more "configuration" (as "configuration A" vs "configuration B".
At a first glance I don't see why repeating this in the endpoint, if the endpoint could simply say "implements" or "conforms to"
