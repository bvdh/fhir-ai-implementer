## Comments

### 1. Grahame Grieve - 2026-10-05

How the validator currently uses UsageContext

The validator uses UsageContext in one place: deciding whether an additional binding applies (R5+ ElementDefinition.binding.additional.usage, or the additional-binding extension before R5). A binding with no usage always applies. A binding with usages applies only if every usage is "in scope".

A usage is in scope in either of two ways:

The person running the validator declares it. They can supply one or more use contexts, e.g. with the -usageparameter, which are parsed into UsageContext values. If a binding's usage matches one of these (same code, and a matching coding in valueCodeableConcept), the binding applies.

It relates the binding to another element in the same resource. This is the case where a value set binding depends on another element:

usage.code.system is the canonical URL (versioned or not) of the profile that declares the binding.
usage.code.code is the path of an element in that profile, e.g. Observation.category.
usage.valueCodeableConcept is the value that element must have.
The validator finds that element in the resource being validated. If it holds a matching Coding or CodeableConcept (same system and code, and the same version if the usage gives one), the binding applies.

When a conditional binding is applied, the validator emits an informational hint that the binding is in scope, and says why. Anything that then fails against that value set can be traced back to the usage that switched the binding on.

Only valueCodeableConcept is supported. Usages valued with Quantity, Range or Reference never match, so a binding that depends on one is never applied.

Checks when validating the profile

For usages that point at the declaring profile, the validator checks two things:

code.code must be a path that exists in the profile's differential or snapshot. Otherwise it's an error.
The value must be a CodeableConcept. Otherwise it's an error.

Usages with any other code.system get a hint that the validator doesn't know what they mean. They can still be satisfied by a use context declared at run time, as in case 1.
