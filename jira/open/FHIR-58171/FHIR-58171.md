- **Description**: When a statusReason references another resource, the actual reason for the status may still not be clear. For example, when referencing an Observation it may be very clear as the Observation describes that in Observation.value. On the other hand, a reference to a Specimen would not be able to convey what it is about the Specimen that provides the reason for the status. For example, the status may be "cancelled" as the test will not be performed, but was it the condition or the volume or something else about the Specimen that cause the status to be cancelled.

One can either use the CodeableConcept of the CodeableReference to indicate the specific reason (e.g., hemolyzed) and then use either .input or .output to reference the Specimen that caused that. OR one can use the CodeableRefernece.concept for the actual reason and the CodeableReference.reference for the Specimen, but that may not be permitted (although the concept is further specified by the reference). OR one can turn the .statusReason into a backbone with a DodeableConcept and a Reference separately so it explicitly can be done together. OR the specimen reject reason and like use cases are addressed through a completely separate attribute or extension.

Using input/ouput is a concern as either could include multiple references and it would be unclear which one is related to the .statusReason.

We suggest that a change of .statusReason to a backbone is most appropriate and minimizes the same concept to be expressed differently based on essentially similar use cases.
