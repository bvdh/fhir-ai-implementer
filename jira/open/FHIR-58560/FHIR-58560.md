- **Resolution Description**: Add a comment to ResearchStudy.recruitment.description to state:

The scope of the description element in the recruitment backbone element is limited to concepts related to the intended study population and the actual study sample. The description may be used to provide human-readable summaries of content that could be found elsewhere as structured data within the recruitment backbone element. The description may also be used to provide additional information such as the rationale for the selected study population or notes about the process used to support recruitment and selection.
- **Description**: `ResearchStudy.recruitment.description` is currently defined only as "Free text description of the recruitment of the study." It is unclear whether this describes:

the recruitment strategy or process
the intended study population
the population actually recruited
differences between the intended and actual recruitment

Please clarify the intended content and its relationship to `recruitment.eligibility`, `recruitment.actualGroup`, `targetNumber`, and `actualNumber`.

## Comments

### 1. BrianAlper - 2026-10-14

In this change request, we should clarify the scope of ResearchStudy.recruitment.description as requested. If an argument is to be made regarding the overall use of description/markdown elements through the ResearchStudy StructureDefinition that should be raised as a separate change request.

### 2. BrianAlper - 2026-10-14

The concepts/guidelines/rules you describe above are relevant for a highly focused resource that is used at a granular level for data exchange with high demands for interoperability. For example and Observation Resource.

However, ResearchStudy Resource is not a granular 'end-node' resource and is used to support many different scopes. The needs for a catalog entry (for ClinicalTrials.gov, EU CTIS, etc.) are not the same as the needs for regulatory reporting (e.g. for M11 CeSHarP) and not the same for automating the conduct of a research study.

Forcing developers and implementers across these widely disparate use cases (some highly descriptive, some highly structured) to follow restrictions that are not responsive to their needs will result in the communities finding solutions to FHIR to meet their needs. There is not a primary critical driver such that research protocol data exchange has to follow the same standard as health data exchange.

### 3. Rik Smithies - 2026-10-13

We need to review all ResearchStudy description-type fields and document how each should be used.

Where two description fields are in scope (e.g. ResearchStudy.description and ResearchStudy.recruitment.description), the definitions need to say what text goes in each. Likewise ResearchStudy.description, .descriptionSummary and .note need to be disambiguated (even if not part of this ticket, needs to be reviewed).

If the distinct use of a field can't be stated, the case for having it is weak.
Options in that case:

Remove it until the use case is understood. It can be added back later or handled as an extension.
Replace it with something more specific. For example, if recruitment.description has two known distinct uses, two specific fields (e.g. recruitment.groupRationale) are better than one general field that could hold either, or anything else that comes along.

Principles (guidelines rather than hard rules, but we should try to follow them):

Each piece of data should have one and only one place in the resource, regardless of profile.
Profiles can narrow a resource but are optional and ignorable. They can't change the meaning of an instance, so "in profile A the data is in field X, in profile B it's in field Y" isn't acceptable. That decision has to be made in core. Non-clinical domains get no exception.
Uncertainty about a field's use isn't a reason to leave it open-ended. A model that's too restrictive leaves nowhere to put data. One that's too open lets different implementers choose different places. Both break interoperability, and the second is less obvious.

General-purpose free-text fields are best avoided. Free text is a hard problem, but if we disagree with these guidelines we should seek clarification.
