- **Resolution Description**: We will update the description of the return (Bundle) output parameter:

The bundle type is "searchset"
A bundle contain a set of Patient records that represent possible matches, optionally it may also contain an OperationOutcome with further information about the search results (such as warnings or information messages, such as a count of records that were close but eliminated) If the operation was unsuccessful, then an OperationOutcome may be returned along with a BadRequest status Code (e.g. security issue, or insufficient properties in patient fragment - check against profile).

If a system needs to assert that two (or more) Patients returned are for the same human, for example, if the operation implementer is an intermediary is connecting to two backend systems with distinct Patient resources, that implementer can communicate the assertion that the two (or more) Patient resources represent the same human patient by including a Person resource, where Person.link.target specifies which Patients represent the same person, and Person.link.assurance indicates the level of confidence.

Note: as this is the only out parameter, it is a resource, and it has the name 'return', the result of this operation is returned directly as a resource|

- **Description**: How is the output of a $match different when there are multiple Patient instances for the same human?

How is the $match count value to be understood when the server has multiple Patient instances that it knows are the same human?

These might be Patient that are linked; or might not.

A specific case is some infrastructure (e.g. HIE) that is in front of multiple real-world EHR that each have their own definition of THAT Patient. Thus a match on a Patient might produce multiple Patient instances, one from each underlying EHR.

We discussed a few options we need to settle on:

Have the intermediary inject a Person resource in the results that links the different Patients that it asserts are the same.
Have the operation intermediary "inject" a Patient.link as the Patient flows through. This has a few problems: 1) if a GET happens to the backend source system, the Patient.link wouldn't be there. The intermediary could swap the FHIR IDs, but that gets... "heavy".
Use Bundle.entry.link to point to other entries in the same bundle. This seems very promising, but we need to identify a code in the link.relation that works.
We might consider a net-new extension on Bundle.entry.
