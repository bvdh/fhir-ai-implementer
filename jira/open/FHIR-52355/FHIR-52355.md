- **Resolution Description**: DRAFT - in discussion about using SUBSET / full resource, and a clients' ability request either.

In operations-for-large-resources.xml, add response sections and Group/List response examples for both $add and $remove.

Add clarifying text:

When the optional return output is present, it SHALL be the same resource type as the target; its relevant repeating array SHALL contain only Group.member or List.entry entries actually inserted or deleted by this invocation, excluding no-op requests and all unchanged entries.

Only required top-level fields plus identity metadata needed for a valid partial resource and the SUBSETTED code in meta.tag are required.

Note that the response is not the complete post-operation target.

Apply the same wording to the return parameters in both $add and $remove.
- **Change Category**: Clarification
- **Change Impact**: Non-substantive
- **Description**: The return value is defined as 'Resource containing content added/removed.' but there are no examples / extra details - it could be interpreted as the entire Group/List resource after the content has been added/removed, or a 'stripped' resource (similar to the one provided in input) listing only the content that has been actually added/remove.

Note that the second interpretation is much better, the first one would force the server to load and send the entire (large) resource, that sort of defeat the purpose of having operations like $add and $remove that operate only by difference.

Requested change: add language and examples that specify that the expected return is a resource with just the added or removed elements.
