- **Resolution Description**: FHIRPath STU3 has extensively refined the functionality referred to in this ticket.

FHIRPath STU3 defines the code system: http://hl7.org/fhirpath/CodeSystem/calendar-units which could be used if desired in places such as Observation.value (quantity), however the fhir Duration profile on quantity only supports ucum where that is used.

The interplay between Ucum definite duration units and fhirpath calendar units is now extensively documented, and where/when explicit/implicit conversions are required in expressions.

Change the content of the "Use of FHIR Quantity" section to the following:

The Mapping from FHIR.Quantity to System.Quantity is only supported for the UCUM (http://unitsofmeasure.org) and FHIRPath Calendar Unit (http://hl7.org/fhirpath/CodeSystem/calendar-units) CodeSystems and a valid code from the system. If any other system or code is present in the FHIR.Quantity, then the engine should throw an error if trying to perform operations/manipulations on the value.

FHIRPath defines how these 2 unit systems are handled in expressions, and when implicit or explicit unit conversions are required between the 2.
Specifically refer to:

Time valued quantities (https://build.fhir.org/ig/HL7/FHIRPath/en/#time-valued-quantities)
Date/Time Arithmetic (https://build.fhir.org/ig/HL7/FHIRPath/en/#datetime-arithmetic)
Time Valued unit conversions (https://build.fhir.org/ig/HL7/FHIRPath/en/#time-valued-unit-conversions)
Quantity equality (https://build.fhir.org/ig/HL7/FHIRPath/en/#quantity-equality)
Quantity equivalence (https://build.fhir.org/ig/HL7/FHIRPath/en/#quantity-equivalence)

Note that the FHIR Duration profile on Quantity only supports UCUM units, and thus expressions writen to interact with this data should use explicit unit conversion where needed.

DRAGON: If your FHIR.Quantity contains 'a' or 'mo' ucum units, these are only equivalent to the calendar units year/month, and as such some operations require explicit unit conversion to be safely evaluated.
These values SHALL not be immediately converted to calendar units, as doing this would prevent safe evaluation of equivalence, equality or date/time addition. Instead the units should only be converted when required to by an operation as described in the fhirpath specification.

Also update the link to the latest version of the fhirpath spec too (consistent with FHIR-54174)
- **Request in-person**: Paul Lynch
- **Description**: FHIRPath defines a set of calendar based units (https://hl7.org/fhirpath/#datetime-arithmetic) so that when adding 1 month, you get the same day of the next month, regardless of the number of days. In many cases this is what systems would prefer over working with the UCUM unit 'mo', which is a specified as 1/12 of the UCUM 'a_j' unit (a Julian year). The proposal here is:

1) Create a CodeSystem for these units defined in FHIRPath
2) Change ValueSets like http://build.fhir.org/valueset-units-of-time.html and http://hl7.org/fhir/valueset-age-units.html to use the new calendar based units (either adding them to the existing lists or replacing as appropriate for the ValueSet's use cases).
3) Replace wording introduced by FHIR-24857 advocating treating 'mo' as a calendar month, with wording recommending the use of the new FHIRPath month unit when calendar months are desired. (Known locations are: http://build.fhir.org/valueset-units-of-time.html, http://build.fhir.org/datatypes-definitions.html#Timing.repeat.durationUnit, and http://build.fhir.org/datatypes-definitions.html#Timing.repeat.periodUnit).

For additional discussion, see: https://chat.fhir.org/#narrow/stream/179266-fhirpath/topic/FHIR-24858/near/296428394
