“The Task resource takes on characteristics of both "requests" and "events" and thus shares characteristics from both patterns” Workflow - FHIR v6.0.0-ballot5

That seems like a recipe for data duplication/state inconsistencies, scope creep, increased implementation variability and the associated degradation of interoperability.

Event resources like Procedure are good.

They capture something that happened with details like what was done, who did it, when and where it happened to whom or what, and why.
Events have status like preparation | in-progress | cancelled | completed
Some events happen and get recorded without anything else needed
Some events are triggered by an explicit Request.

Request resources like ServiceRequest are good.

They capture an order that something should/is authorized to happen with details like what they would like done, by whom maybe, when-ish, etc.
The resulting event references the Request.
Sometimes there is no need to instantiate any coordination or intermediate state between the Request and the Event(s).
Sometimes it helps to have a resource (Task) as workflow "glue" between the Request and the Event.

Task can hold tentative selection/assignment of performers and other resources, scheduling, etc.

Task should reference the Request, not introduce elements that duplicate the content of the request. Duplication opens the door to inconsistent information and makes systems have to look in multiple places instead of just one (and sometimes get different answers and need logic to deal with that). Does the Task.requestedPeriod contain the same value as the ServiceRequest.occurancePeriod? What do the differences between the ServiceRequest.status and the Task.status mean? Does Task.status reflect the request status, the workflow status, or the resulting event status? Does Task.priority and .intent reflect the ServiceRequest.priority and .intent?
If ServiceRequest is not adequate as a generic Request resource, then introduce a GenericRequest and Task can reference it.

Task should reference the resulting Event(s) (or arguably, they should reference the Task since Task may exist during planning prior to the event), not introduce elements that duplicate the content of the event. If Procedure is not adequate as a generic Event resource, then introduce a GenericEvent and Task can reference it.

If Task tries to fill three roles at once (the Request, and the Event, and the Workflow execution in between), tension between those roles will manifest.

Task should focus on the workflow execution details; marshalling/scheduling/notifying during the fulfillment of a (referenced) Request.

Or you can start beefing up the guidance text to mitigate all the overlaps and duplications. And write up why this seemed like a good idea at the time.
