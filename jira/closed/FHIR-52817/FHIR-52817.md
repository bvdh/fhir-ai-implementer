## Comments

### 1. EssienGe - 2025-09-25

Thanks ehaas , I'm just aware of this.

Then maybe make more clear in the description to avoid misunderstanding. Previously I thought you just put compact serializations into signature.data directly and calling it based64. That's why we raise this ticket. Your proposal above is much clearer but I would suggest to put in serialization in the wording, and maybe clearly state both are supported.
The Signature.data is a base64 encoding of a JWS-Signature specified in RFC 7515: JSON Web Signature (JWS) . In other words, the field contains the JWS signature, which is generated and serialized according to the JWS specification (e.g. compact serialization, json serialization) and then encoded in base64.

BTW, If we want to support both compact and json serializations, one next question is do we need an element to distinguish them? Seems the sigformat cannot do that for now. Or do we leave it for verifier to decode and then judge by themselves?

### 2. Eric Haas - 2025-09-24

We do not restricting JWS to only compact serialization. For example, if you want to use unprotected headers or multiple signatures, it would be JSON serialized according to IETF RFC 7515 section 3.2.

Even if it is a JWS compact serialization is it still base64 encoded since the FHIR Signature.data datatype is base64Binary which means your treat the JWS as just another string. In other words you are base64 encoding base64 encoded strings.

### 4. Eric Haas - 2025-09-24

The JWS signatures are created following the referenced specifications and then subsequently base64 encoded before they get added to the Signature datatype.

Clarify the following text to make it clearer
The Signature.data is a base64 encoded JWS-Signature as specified in RFC 7515: JSON Web Signature (JWS) . In other words, the field contains the JWS signature, which is generated according to the JWS specification and then encoded in base64.
