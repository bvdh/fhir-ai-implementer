- **Resolution Description**: In the section on if-none-exist, will add a dragon warning that says:

"In most database technologies, searching for existing records does not create a 'lock' that would prevent new records from being created. It is possible for a race condition to exist where the search indicates that no matches exist, but before the create is executed, a record comes to exist. Servers may pursue different strategies to minimize this risk (e.g. querying that "only one exists" after creation but before committing), but it usually can't be fully eliminated.

Servers MAY check for multiple if-non-exist creates within a single transaction and check for possible collision prior to executing."

- **Description**: The fundamental problem is that you can't solve this for arbitrary search criteria in an efficient way.

An example for Conditional Create, where there are 2 competing request, the first uses:
If-None-Exist: identifier=http://lab|123&patient=Patient/456
The second uses:
If-None-Exist: identifier=http://lab|123&patient.name=Smith

Both requests should logically resolve the same underlying resource. If they both happen at the same time they get different IDs and we now have duplicate resources with different IDs.

Everything from here is a workaround:

Choose a piece of information to lock on (domain specific)
Search -> Persist -> Search to ensure a duplicate wasn't created

I understand it leaves this to implementors, but this will create divergence in behavior.
