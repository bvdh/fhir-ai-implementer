- **Resolution Description**: Add extension to the extensions pack:

Extension: complies-with-canonical

Official URL: http://hl7.org/fhir/StructureDefinition/complies-with-canonical

Standards status: Trial-use

Maturity Level: 1

Computable Name: CompliesWithCanonical

Description:

Indicates that a resource or element complies with another formally defined canonical resource. This extension allows systems to declare that their implementation satisfies multiple canonical definitions beyond the primary one referenced in corresponding 'definition' elements.

Context of Use:

Element ID: SearchParameter
Element ID: CapabilityStatement.rest.searchParam
Element ID: CapabilityStatement.rest.resource.searchParam
Element ID: OperationDefinition
Element ID: CapabilityStatement.rest.operation
Element ID: CapabilityStatement.rest.resource.operation

Value Type: canonical

Comments:

Compliance means that an implementation of a canonical resource (e.g., a search parameter or operation) satisfies all the normative requirements of the referenced canonical resource definition. When an implementation states that it complies with multiple canonical definitions, it means that it simultaneously satisfies all mandatory requirements from each referenced definition. This enables a single implementation to declare conformance to multiple sources without having to duplicate capability statement entries.

- **Description**: In FHIR-I, there was a request for clarity around tickets:

https://jira.hl7.org/browse/FHIR-48876 (CGP): How to deal with searchparameters in the package that only convey expectations
https://jira.hl7.org/browse/FHIR-46036 (CGP): Derive composite search parameters for derived normal parameters

The question is centered around a set of conflicts:

Core-defined search parameters leave elements like multipleAnd as implementer discretion
There is no method, other than a SearchParameter definition, to declare support for those elements.
Since there is no multiple inheritance, servers are thus unable to declare support for two different derived parameters, even if they are compatible.

This results in servers being unable to say they conform to, for example, two different national profiles that both apply the same rules.

My understanding is that this scenario then leads to authors recommending that servers do not use their SearchParameter definitions, since it is problematic.

If we allow for declaring support of those requirements in another place (e.g., CapabilityStatement, Feature Capability IG), IGs would be able to describe requirements and servers would be able to advertise support more consistently.
