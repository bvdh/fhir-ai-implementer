- **Resolution Description**: Background:

Three distinct identifier/version concepts coexist in a FHIR Document and are not clearly delineated where readers encounter them:

Resource.meta.versionId — the server-assigned technical version of any resource instance (referenced obliquely in the current comment as "its own version identifier").
Composition.version (this element) — the author-assigned logical version of the Composition as a whole; maps to CDA versionNumber.
Bundle.identifier — identifier of a specific document instance produced by $document; analogous to CDA ClinicalDocument.id.

The current comment alludes to all three without naming any of them confusing the reader.

Changes

Rewrite the Composition.version comment to name the contrasting concepts explicitly.

from:
While each resource, including the composition itself, has its own version identifier, this is a formal identifier for the logical version of the Composition as a whole. It would remain constant if the resources were moved to a new server, and all got new individual resource versions, for example.
to:
This element is the author-assigned business version of the Composition (analogous to CDA ClinicalDocument.versionNumber). It is distinct from Resource.meta.versionId, which is a server-assigned technical version that every resource carries and that may change whenever the resource is updated on a server. Composition.version reflects the version of a logical document's content and remains constant even if the Composition or its referenced resources are moved between servers and receive new meta.versionId values.
2. Update the "Note for CDA aware readers" section of the Composition page to list all CDA relevant identifiers in one place: ( rather than scattered across the mapping table)

change 1st bullet in:

2.8.3.3 Note for CDA aware readers

Many users of this specification are familiar with the Clinical Document Architecture (CDA) and related specifications. CDA is a primary design input to the Composition resource (other principal inputs are other HL7 document specifications and EN13606). There are three important structural differences between CDA and the Composition resource:

A composition is a logical construct - its identifier matches to the CDA ClinicalDocument.setId. Composition resources are wrapped into Document structures, for exchange of the whole package (the composition and its parts), and this wrapped, sealed entity is equivalent to a CDA document, where the Bundle.identifier is equivalent to ClinicalDocument.id and Bundle.meta.security is equivalent to ClinicalDocument.confidentialityCode.
The composition section defines a section (or sub-section) of the document, but unlike CDA, the section entries are actually references to other resources that hold the supporting data content for the section. This design means that the data can be reused in many other ways.
Unlike CDA, the context defined in the Composition (the subject, author, event, event period and encounter) apply to the composition and do not specifically apply to the resources referenced from the section.entry. There is no context flow model in FHIR, so each resource referenced from within a Composition expresses its own individual context. In this way, clinical content can safely be extracted from the composition.

In addition, note that both the code lists (e.g., Composition.status) and the Composition resource are mapped to HL7 v3 and/or CDA.
to:

A Composition is a logical construct. Composition and the resources referenced in its sections are wrapped into a document Bundle for exchange of the whole package (the composition and its parts). In FHIR a CDA document is represented as a document Bundle. The CDA document identifiers map as:

ClinicalDocument.id ↔ Bundle.identifier,
ClinicalDocument.setId ↔ Composition.identifier,
and ClinicalDocument.versionNumber ↔ Composition.version.

In addition, ClinicalDocument.confidentialityCode is equivalent to Bundle.meta.security. For other CDA mappings to Composition, see the mappings page.
