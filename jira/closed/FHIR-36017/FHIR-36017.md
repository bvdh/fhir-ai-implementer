8.9.6 Notes

The IHE connection types that were defined in R4 have been moved to IHE defined profiles and vocabulary at https://profiles.ihe.net/ITI/mCSD
Endpoint.period is meant to represent the general planned period of time when the Endpoint may be used, for example when an endpoint is being commissioned or decommissioned. It is not meant to account for temporary downtimes or other short terms changes of availability. For example, if an Endpoint is only available during business hours (9-5), the lack of availability during the night would not be reflected in Endpoint.period.

A new Endpoint.availability property will be added:

Endpoint.availability 0..1 Availability

Definition: The times the endpoint is expected to be available, including transient downtimes and any exceptions.

Comments: Endpoint.availability is meant to represent specific availability, including temporary downtimes or other short term changes in availability. Conversely, Endpoint.period is meant to represent the general planned period of time when the Endpoint may be used, for example when an endpoint is being commissioned or decommissioned. For example, if an Endpoint is only available during business hours (9-5), the lack of availability during the night would not be reflected in Endpoint.period, but would be reflected in Endpoint.availability.

HealthcareService, Location, and PracitionerRole will have their availability properties updated to be 0..1, as the multiple cardinality is represented within the Availiability metadata type.

Endpoint.status will be updated:

Definition: The endpoint status represents whether the endpoint can currently be used for connections or why it can't be used.

Comments: This element is labeled as a modifier because the status contains codes that mark the endpoint as not currently valid.

Short Display - "test" will be removed, as part of cleanup from FHIR-27934

We will fix the entered-in-error status to have a definition that isn't specific to the patient's medical record.

## Comments

### 1. Cooper Thompson - 2023-04-05

The comments on the period clearly define that the temporary downtimes or other short term changes are not covered by this, it's just when it's expected to become available, and when it will be retired.

There is a new DataType "Availability" that Patient Administration is creating to cover availability that could be used in an extension to provide fine grained availability information. (refer to FHIR-25381)

Just relying on Endpoint.status would not permit forward planning for activation/deactivation rather then discovering it was off. The status can provide direct input on the current details, but not planning.

e.g. The endpoint status might be indicating suspended, or error but be within the period which would indicate that the service should be active (via the period) but there is some condition causing the inactivity, and that should become active again, or call the managing organization to determine what is going on.

On reviewing the comments/definitions on status/endpoint, we agree that we can add additional clarifications on the interplay between status and period.

Another case where the start date can be very useful is where you may be switching over between systems, and one has an end date, and the new one has the start date to take over.

### 2. Brian Postlethwaite - 2022-07-13

PA Conference call 13 July 2022:

We've also checked 4 different implementation guides if any of them have profiled additional usage information into the endpoint.period, and only the VhDir guide even includes it as a must support. The Australian secure messaging spec ignores it, as does the US National Directory project IG(s).

Will follow up with some other implementers to see what is going on here.

### 3. John Moehrke - 2022-05-16

If the intent is to support use-cases where the endpoint is currently not active, but will be in the future... then period is not the right datatype. You don't seem to be using both values in period, and period start and/or end are unclear on a use-case where the endpoint is now not available but will be available in the future. Is it start of availability, or end of unavailability? How precise and/or accurate is a consumer to trust this future date? I am also not convinced this is enough use-case to support a core element, should this be an extension?

The status when not up is still a bit unclear. I presume that status would always represent the truth. So it would not be active when it is not active, and when it becomes active it will indicate active.
