# FHIR-48862: Request pattern - provide guidance on "proposals for requests" and how the statuses are typically expected to evolve

- **Resolution Description**: Will update "Fulfillment/Execution information" to add:

"Irrespective of the Request.intent, changes to the status of the Request should always be under the control of the requester and be a reflection of changes to the recommendation/authorization. For example, a Request should only change to 'complete' when the requester determines that the action they requested has been completed as ordered (or sufficiently close to what was ordered). For further clarity, the status of a Request (e.g. a proposal) is NOT generally changed automatically when a fulfilling Request (e.g. an order) or Event is created or has its own status changed.

If there is no closed loop process that allows the requester to evaluate what was done, then the status of a request might never change from 'active' or might only be changed to 'ended' when the system automatically updates the status when recommendation/authorization has expired.

If there is a need to track 'status of fulfillment' on a Request, this could be done with a fulfillment Task, possibly as a contained resource."

- **Description**: The state machine for orders/authorizations is one where the authorization status doesn't reflect the status of the fulfilment. This pattern can be used also in authorizations (for example those used in DSS) - a proposal for requesting a medication can for example have status "active" regardless of whether the medication request is actually started or considered.
